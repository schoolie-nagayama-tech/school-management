# 保護者への返信をAIで支援する（設計書）

作成: 2026-09-02 ／ 更新: 2026-09-02（方針確定）／ 状態: **確定・実装待ち**
対象: `/admin/portal-chat`（教室側の保護者チャット受信箱）
前提: [docs/ai-platform-comparison.md](./ai-platform-comparison.md)（基盤＝Claude API）、
[docs/lesson-report-flow-plan.md](./lesson-report-flow-plan.md) の⑭で得た教訓（**AIに書かせると文がAIっぽくなる**）

## 0. 結論（先に）

1. **振替と模試は「機能で処理する」が正しい方針だが、現状はまだ機能が足りていない。**
   - 振替: 受付の自動返信と「確定後の通知」は実装済み。しかし **保護者が出した候補日（第1〜3希望）は chat の payload に埋もれ、座席表と一切つながっていない**。可否の判断・返信は毎回手書き。
   - 模試のリマインド: **未実装**（自動の催促・前日連絡・当日確認はゼロ。マイページを開いたときに「申込プッシュ」が表示されるだけのプル型）。
   → この2つはAIではなく**ロジックと定型文**で埋めるべき穴。本書では「返信AI」の対象外とし、別タスクとして切り出す（§6）。

2. **返信AIの対象は、それ以外の「人が考えて書く返信」。** 受験・進路の相談、宿題・学習の相談、体調、退塾、事務（教材・請求・時間変更）。実データでは件数は少ないが、1件あたりの負荷が重い。

3. **作り方は⑭講評と同じ「整える」を主軸にする。** ゼロから書かせない。教室長が書いた返信を整えるか、教室長の方針（箇条書き）から**型に沿って**下書きする。挨拶・結びの定型は実データから固定し、AIが触るのは本文の1〜3文だけ。

4. **クレームはAIに書かせない。実務どおり電話で対応し、システムがやるのは「上席へのアラート」。**（2026-09-02 決定。§3.1）

## 2. 実データから分かった返信の型（生徒コミュニケーション 200件・113スレッド）

> 添付の docx には検索一覧の見出しに「472件」とあるが、本文まで書き出されていたのは先頭数ページぶんの **200件**（3つの検索結果の混在）。傾向を掴むには十分だが母数はその前提。

**話題の分布（スレッド数）**: 振替 43 ／ 欠席 18 ／ 模試 14 ／ 事務 10 ／ その他 11 ／ 退塾 3 ／ 講習 4 ／ 受験・進路 3 ／ 部活・生活 2 ／ 宿題・学習 2 ／ 面談 2 ／ 体調 1。
振替・欠席・模試の「日程調整」で過半数（75/113）。**返信AIの対象（相談・事務・体調・退塾・その他）は合計 31 スレッド＝約3割**。件数は少ないが、1件ごとに考える負荷が高い。

**教室側の返信の型（95件）**:
- 平均 **128字**（講評の176字より短い）
- 冒頭「（いつも）お世話になっております」 54%、結び「よろしくお願いいたします」 43%
- 構造: **挨拶 → 承知／お礼の一言 → 具体的な回答 → 結び**。ほぼ全件この型。
- 相談系はこの型の中に「共感 → 具体策（数字・日程）→ 講師との連携を示す → 必要なら面談へ」が挟まる。
- **約束できないことは約束しない**（「確認のうえご連絡します」）。原因不明でも「ご迷惑をおかけしました／今後このようなことがないよう努めます」で着地。退塾は引き止めない。
- **生徒本人からのメッセージは口語＋励まし**で、保護者向けの定型は使わない。

## 3. AIが担うこと・担わないこと

| | AIが担う | 担わない（ロジック／人） |
| --- | --- | --- |
| 振替の可否 | 可否の結果を文にする | **可否の判定**（候補日 × 座席表の空き）＝ロジック |
| 模試の案内 | — | 定型＋cron。AI不要 |
| 欠席のみの連絡 | — | 既存の自動受付返信で完結 |
| 相談・事務・体調・退塾・その他 | **教室長の返信を整える／方針から下書き** | 方針を決めるのは教室長 |
| 生徒本人からのメッセージ | — | **対象外**（トーンが違う。AIを出さない） |
| クレーム・事故対応 | 分類して**上席にアラートを上げる**まで | 対応は電話。文面もAIに書かせない |

**原則（⑭講評と同じ）**: 事実を足さない・削らない。教室長の言い回しを残す。何を直したか全部出す。出力は必ず編集可能。

### 3.1 クレームは「返信を作る」のではなく「上席に上げる」（2026-09-02 決定）

実務ではクレームは**電話で対応する**。チャットで長文を返すこと自体が筋が悪いので、
AIの仕事は文面ではなく**気づくのが遅れないこと**に置く。

- **判定はAIだが、出力は分類だけ**（`level: none | watch | escalate` と根拠の引用1文）。返信文は作らない。
- **教室長の明示操作も並べて置く**。受信箱の各スレッドに「上席に相談」ボタン。AIが拾えなくても人が上げられる経路を必ず残す（AIの取りこぼしが放置につながらないように）。
- 通知先は `src/lib/slack.ts` の Incoming Webhook を再利用し、教室の `slack_mention_id` をメンションする。新しい通知基盤は作らない。
- **感度は高めでよい**。見逃しの損害が大きく、過検知のコストは「上席が1件読む」だけ。ただし
  `escalate` は保護者には一切見えない（内部通知のみ）。
- 通知に載せる: 教室・生徒・スレッドへのリンク・保護者の原文（要約しない）・検知理由。
  **AIの解釈で上書きしない**（伝言ゲームで温度が変わるのを防ぐ）。

## 4. UI（`/admin/portal-chat` の返信欄に足す）

返信欄（Textarea）の直下に2つのボタンを置く。画面を作り直さない。

### 4.1 「整える」（Phase 1）
教室長が返信を書いてから押す。⑭講評の「整える」と同じ作り。
- 直すのは: 誤字・表記ゆれ／長すぎる一文／保護者に伝わりにくい言い方／**挨拶と結びの定型が抜けていれば補う**（実データの型に合わせる。これだけは「足す」）。
- 出力: 整えた本文（編集可）＋「直したところ」（before → after ＋理由、**1か所ずつ戻せる**）＋「残したところ」。
- 材料: 返信欄の本文 ＋ スレッドの直近の保護者メッセージ（文脈を読むため）。

### 4.2 「下書き」（Phase 2）
教室長がまだ書いていないときに押す。**方針の箇条書きを必須**にする（空なら押せない）。
- 入力: 保護者のメッセージ（スレッド直近 1〜3件）＋ 教室長の方針（箇条書き）＋ 話題の種別（相談／事務／体調／退塾／その他。AIが推定して表示、教室長が直せる）。
- 出力: 型（挨拶→承知→本文→結び）に沿った下書き。**本文はAIが書くが、方針にないことは書かない**。実データの言い回し（§2）を参考として渡す。
- 話題別の「守ること」をプロンプトに固定する:
  - 相談: 共感を先に。具体策は方針にあるものだけ。決められないことは面談へ。
  - 事務: 次のアクション（発注する／持ってきてほしい物／日時）を明確に。
  - 体調: 無理をさせない。復帰日と振替は「様子を見て相談」で締める。
  - 退塾: 引き止めない。感謝＋手続きの案内。
  - クレーム: 下書きしない（§3.1 のとおり上席アラートへ回す）。
- 出力は編集可。「もう少し短く／ていねいに／元の言い方を残して」で作り直し。

### 4.3 送信まわり
- AIの下書きを**一度も編集せずに送ろうとしたら確認**を1枚挟む（「AIの文のまま送ります。内容は確認しましたか」）。⑭講評での「AIっぽさ」の教訓を、送信前に1回だけ思い出させる。
- 送信APIは既存の `POST /api/admin/portal-chat/messages` をそのまま使う。**保存経路を増やさない。**

## 5. サーバー側

- `POST /api/ai/reply/tidy` と `POST /api/ai/reply/draft`（Route Handler、サーバーのみ）。既存の認証作法（`getApiAuth` 系）でスレッドの教室スコープを検証。
- クレーム判定は返信APIとは別に `POST /api/ai/reply/triage`（受信時に呼ぶ）。分類だけを返し、文章は返さない。
- モデル: Haiku 4.5（整える・判定）／Sonnet 5（下書き。相談系は日本語の質が効く）。Vercel AI SDK 経由。
- **AIに渡す情報はホワイトリスト**: スレッドの直近メッセージ本文、生徒の学年・科目、教室長の入力。成績・出欠・面談記録は**教室長が「渡す」にチェックしたときだけ**添える。住所・電話・LINE ID・支払い情報は渡さない。
- 保護者の文面には氏名が入るため仮名化はしない（委託として整理。`docs/legal/privacy-policy.md` 第5条に Anthropic を追記＝公開前必須）。
- ログ: プロンプトと出力はDBに保存しない。使用量（トークン）だけ日次で集計してアラート。
  ただしクレーム判定だけは**上げた／上げなかったの記録を残す**（見逃しの検証に要る。本文は残さずスレッドidと判定のみ）。

## 6. AIではなく「機能」で埋める2つの穴（別タスク）

> 2026-09-02 決定: この2つは **AIヘルプ機能と同じ扱いの独立タスク**として登録する。
> 返信AI（Phase 1）を先に進め、こちらは並行の別タスクとして起こす。

### 6.1 振替候補日 × 座席表（効果は最大）
実データで最多の話題。いまは候補日が payload に埋もれ、教室長が座席表を別途開いて空きを確かめ、手で返信し、確定後に通知ボタンを押す＝4工程。

- 保護者の候補日（`payload.candidates`）を受けた時点で、**座席表の空き（その生徒の科目・講師で置けるコマ）と突き合わせて可否を自動判定**する。判定は既存の `checkTeacherFit` / `evaluateStudentDrop` と同じ意味論を使う（画面と判定がズレる罠を作らない）。
- 受信箱に「第1希望 ○ ／ 第2希望 ×（講師が満席）／ 第3希望 ○」を表示し、**その場で振替を確定 → 既存の確定通知を自動送信**まで一気通貫にする。
- AIの出番は、可否が決まった後の**文面**だけ（§3）。可否をAIに判断させない。

### 6.2 模試のリマインド
自動化ゼロ。cron（`vercel.json`）に1本足し、定型文を LINE/マイページへ送る。
- 申込締切の3日前（未申込の対象学年）／ 実施日の前日（申込済み）／ 当日受験か別日かの確認。
- 文面は定型で足りる。AI不要。

## 7. フェーズ（2026-09-02 確定）

1. **Phase 1（先に進める）**: 返信欄に「整える」（§4.1）。サーバー `/api/ai/reply/tidy`。送信前確認（§4.3）。
2. **Phase 1.5**: クレームの上席アラート（§3.1）。「上席に相談」ボタン → Slack。AI判定は後から足せる形にしておく。
3. **Phase 2**: 「下書き」（§4.2）と話題別ルール。
4. **別タスクA**: 振替候補日 × 座席表の自動可否＋一気通貫（§6.1）。
5. **別タスクB**: 模試リマインド cron（§6.2）。

**順番の理由**: Phase 1 は既存の返信文を整えるだけなので失敗しても被害が小さく、⑭講評の「整える」とコードを共有できる。別タスクAは件数が最多で効果が大きいが、座席表の判定ロジックと結合するため独立して進める。

## 8. 決定事項（2026-09-02）

1. **クレームはAIに書かせない**。実務どおり電話対応とし、システムは上席へのアラートを担う（§3.1）。
2. **「下書き」は Phase 2 に回す**。まず「整える」から入る（講評で懲りた点を踏まえて）。
3. **返信AIを先に進める**。振替の一気通貫（§6.1）と模試リマインド（§6.2）は、AIヘルプ機能と同じく**独立したタスクとして登録**し、並行で扱う。
