## P0. M1（講師リリース）準備 — 6/15〜6/30

### 目的

講師が「匿名の出欠ポータル」ではなく**本物のアカウント**で運用を始められるようにする。これにより `project_rls_security_remediation` の最大の残穴（attendance系 anon フルCRUD）を塞ぐ前提が整う。

### タスク

1. **講師アカウント発行フロー検証**（既存 `user_invitations` 流用）
   - 既存の招待発行（`/api/admin/users` 系・`requireAdmin`/`requireManager`）が teacher ロールで機能するか確認。
   - 招待メール文面・有効期限（7日）・QR/URL の配布手段を確定。
2. **出欠ポータルの認証化**
   - 現在 anon で動く出欠記録（attendance）/シフト提出（regular_shift）を、ログイン済み講師の操作へ移行。
   - `regular_shift_submissions.user_id` 未設定問題（現状 email マッチで誤魔化し）を、本物の `user_id` 紐付けへ是正（`schedule-system-handoff.md` 残課題5）。
3. **講師向け画面の最終確認**
   - 当月出勤簿・本日の授業・出欠入力・報告書入力・シフト提出（モバイル）。
   - `ui_redesign_plan` の「teacher→自分の当月出勤簿に着地」を最小実装（ロール別ルーティングの先行部分）。
4. **RLS封鎖の準備（適用は運用切替後）**
   - `zzz_` 接頭辞で `attendance_*` / `regular_shift_*` / `user_profiles` / `user_schools` の anon ポリシー削除マイグレーションを**用意**（適用は全講師の認証移行完了後＝M1末）。
   - 封鎖前チェックリスト: components/forms 配下と各 lib の anon 直読を実コードで確認（`subjects` 誤削除リグレッションの教訓）。

### テスト

- ユニット/APIルート: 招待発行・受諾、出欠記録APIの認証ガード（`authSuccessMocks`/`authFailMocks`）。
- 統合（ローカルSupabase）: teacher ロールでの attendance CRUD が RLS で通る/anon で弾かれる。
- 手動E2E: 講師1名で「ログイン→シフト提出→出欠入力→報告書」を実機で通す（プレビューデプロイ）。

### リスク / 依存

- ⚠️ 出欠ポータルを使う既存運用がある場合、切替日を全講師に周知。anon封鎖は**全員の移行確認後**（途中で封鎖すると現場が止まる）。
- 封鎖は段階的に: ①移行 → ②数日並走（anon温存） → ③封鎖。

### 出口条件

- [ ] 全講師に本番アカウントを配布

正典 `docs/account-line-design.md`。保護者機能の足回り（アカウント・認証・LINE）を作る。

### 0. LINE取得（最優先・P1から継続）

> **現状（2026-08-05 取得完了）**: 公式アカウント「スクールIE」@315raggk（フリープラン）＋Messaging API/LINE Login 2チャネル作成済み・認証情報を .env.local / Vercel env に登録済み（`LINE_MESSAGING_CHANNEL_SECRET` / `LINE_MESSAGING_ACCESS_TOKEN` / `LINE_LOGIN_CHANNEL_ID` / `LINE_LOGIN_CHANNEL_SECRET`）。開発中はフリープランのままで問題なく、**M2の約1ヶ月前を目安にスタンダードへ変更**する。

1. LINE公式アカウント開設。
2. LINE Developers でプロバイダー作成 → 同一プロバイダー内に **Messaging APIチャネル** ＋ **LINE Loginチャネル**。
3. 各チャネルの認証情報を環境変数登録（Vercel env）。
4. プラン: スタンダード¥15,000/月 前提（報告書を毎回LINE通知＝シナリオ③）。月単位で変更可なので様子見でライト降格も可能。

### 1. データモデル（生徒テーブルは無変更）

- `portal_accounts`（保護者・生徒統合・PIIなし: line_user_id / login_id / password_hash / display_name …）
- `portal_account_students`（多対多: account_id / student_id / relation=self|guardian|other・relation_note=otherの自由入力）
- `portal_invitations`（token / student_id / invite_type=guardian|student / expires_at=7日 / accepted_*）

### 2. 認証・セッション（案3: 自前ログイン → Supabase互換JWT → RLS）

- LINEログイン or 教室発行ID/PW を自前検証 → `sub=portal_account_id` のSupabase互換JWTを署名発行 → RLSで `auth.uid()` 認可。
- **実装前に最優先で検証**: 「自前JWTをSupabaseのJWTシークレットで署名 / Third-Party Auth登録 → RLSが受理」する技術PoC。ここが通らないと案を見直す必要があり、**P2の最初にスパイクとして実施**。
- ポータルが読むテーブル（students / schedule_entries / 報告書等）に、スタッフ用と**併存**するポータル用RLSポリシーを追加。

### 3. 招待・オンボーディング・失効

- 招待発行（教室）: 生徒選択 → invite_type 指定 → コード/QR/URL生成。配布=紙QR/URL印刷＋メール（`form_responses.email` 流用可）。
- オンボーディング: 友だち追加 → LIFF/Webで「LINEでログイン」→ portal_accounts 自動作成 → 招待コードで紐付け。兄弟は2人目の招待コードで行追加。LINE無し生徒は教室発行ID/PW。
- 失効: `students.withdrawal_date` 超過で当該生徒の紐付けを RLS で自動失効（卒業/退塾後は即時閲覧不可）。

### テスト

- 認証ブリッジのPoCを最初に通す（最大の技術リスク）。
- 統合テスト: ポータルJWTで自分の紐付け生徒のみ読める／他生徒は弾かれる（RLS多層防御の核心）。
- 招待トークンの有効期限・使い切り・失効のテスト。

### 出口条件

- [ ] LINE 3チャネル取得・env登録
- [ ] 認証ブリッジPoC成功（案3が技術的に成立）
- [ ] portal_* テーブル＋RLSポリシー作成

## P3. 保護者向け機能実装 — 11月〜1月

`account-line-design.md` §9。保護者が触れる面はマイページ＋**3ドメイン（スケジュール／報告書／コミュニケーション）**。チケット詳細は付録 P3-S/R/C/X。

**確定した方針（2026-06-15）**:

- 欠席連絡 = **専用導線を作る**（保護者発信。座席表・振替フローと連動）
- 報告書の保護者公開 = **室長承認後に公開**（講師下書き→室長承認→公開）
- 報告書公開のLINE通知 = **毎回push**（スタンダード¥15,000/月 前提。後でまとめ切替の余地は残す）

### 0. マイページ（擬似認証 student-dashboard を置換）

- 3ドメインを束ねる器。**請求は出さない**（別管理）。生徒(self)には保護者向け情報を出さない（権限は invite_type で確定）。

### S. スケジュール機能（保護者向け）★座席表が絡む本丸

- 時間割・今後の予定ビュー（紐付け生徒の schedule_entries、種別＝通常/振替/講習/テスト対策/体験/休講を凡例付き表示）。
- 予定変更（振替・休講・コマ変更）を検知して LINE 通知。
- **既存ポータルフォーム（youbi/shukaisu/zoukoma/moshi/mogi/soudan）を擬似認証→本物アカウントへ移行**し、回答を本人/紐付け生徒スコープに（RLS）。
- **欠席連絡 専用導線**: 保護者が時限を選んで欠席/遅刻/振替希望を送信→教室が受付（座席表・振替フロー連動）。
- 面談/体験セルフ予約（INQ予約系）を保護者ログイン文脈に接続。

### R. 報告書機能（保護者向け）

- 報告書 保護者ビュー = **P1-14 報告書×進行表マージの「ビュー2」**。
- **公開承認ワークフロー**: 講師下書き→室長承認→公開。承認前は保護者非表示。
- 公開時に**毎回LINE通知**。宿題は報告書記述から抽出して表示（専用データは作らない）。過去報告書の一覧・履歴。

### C. コミュニケーション機能（保護者向け）

- ④ 1対1チャット: `chat_threads`/`participants`/`messages`/`reads`。相手は教室（室長）宛1本、スレッドは生徒ごと、参加者は室長指定。新着は「新着あり」を1通集約でLINE push。
- ⑤ 掲示板拡張（既存 BulletinBoard 拡張）: `audience`（社内/保護者/生徒・複数可・既定=社内）＋配信単位（全体/学年/個別）。portal 既読は reader_kind or 専用テーブル。一斉連絡=LINE push。
- LINE通知基盤＋切り分け（届ける=push／見れば済む=LIFF閲覧0円）＋通数ログ（コスト管理）。

### L. 法務・コンプライアンス（★M2リリースの前提ゲート）

保護者・生徒の個人情報を公開する以上、リリース前に必須。**P2〜P3で策定を先行し、確定・公開はM2前**。文面はオーナー/専門家のレビュー・承認が前提（エンジニアは設置面と同意フローを提供）。

- **プライバシーポリシー**: 利用目的／取得項目／第三者提供／**LINE・Resend 等への外部送信**／保存期間／開示・訂正・削除請求の窓口。
- **利用規約**: ポータル利用条件・禁止事項・免責・準拠法・問い合わせ先。
- 公開ページ（/privacy・/terms）設置＋招待/ポータル導線からリンク。
- **同意取得フロー**: 招待受諾/初回ログイン時に同意必須、**同意ログ保存**（誰が・いつ・どの版に同意したか）。
- **外部送信規律（改正電気通信事業法）** 対応の確認。**未成年（子ども）の個人情報・保護者同意**の整理（個人情報保護法）＋データ保存期間ポリシー確定（P4と統合）。

#### 法務の注意点メモ（策定時に潰す。※専門家・オーナー確認前提）

1. **委託先の海外保管＝「外国にある第三者」規律**（見落とし注意）: Supabase(ap-southeast-1=シンガポール)・Vercel・LINEヤフー・Resend は個人データが**国外保管**になりうる。委託でも越境規律の対象 → 本人同意 or 基準適合体制＋情報提供が必要。利用目的＋委託先＋保管国を整理。
2. **委託先の監督義務**: 上記SaaSは個人データの取扱い委託先。各社のDPA/利用規約・保管リージョンを確認し記録（安全管理措置の一部）。
3. **要配慮個人情報**: 成績は該当しないが、健康・障害・配慮事項を扱うなら要配慮＝**原則取得同意必須**。マイページ/チャットに機微情報を載せない設計か確認。
4. **改正電気通信事業法・外部送信規律**: LINE連携・アクセス解析・タグ等で利用者情報を外部送信するなら確認措置（公表等）が要る。
5. **特定電子メール法（Resend送信）**: 広告宣伝メールはオプトイン・送信者表示・配信停止導線が必須。問合せ追客メールが広告に当たるか線引き（報告書通知等の事務連絡は該当しにくい）。
6. **LINE規約**: Messaging API/公式アカウント規約の遵守、配信への同意、ブロック（配信停止）手段の確保、取得情報の利用目的明示。
7. **漏えい時対応**: 個人情報保護委員会への報告＋本人通知の義務（一定の場合）。手順を runbook 化。
8. **開示・訂正・利用停止請求の窓口**と社内対応フロー。**同意の版管理**（規約改定時の再同意）。
9. **本部FC（スクールIE）との関係**: 本部の個人情報規程・ブランド/データ共有方針との整合（問合せは本部HP経由で取得＝取得経路・第三者提供の整理）。
10. **退塾後のデータ保存/削除ポリシー**（P3-L6・P4-5）。問合せ側の未入会者PII（880件移行）も利用目的・保持期間を整合。

### テスト

- コンポーネント/統合: チャット送受信・既読、掲示板 audience フィルタ、マイページの権限境界（self に請求/保護者情報が出ない）。
