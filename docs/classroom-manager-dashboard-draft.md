## 確定方針（2026-06-06 ユーザー確認済み）

- **ルート**: `/home` を新設。`manager` 以上はログイン後ここに着地。`teacher` は従来通り（`/today` 等）。UI redesign 計画の `/home` 構想と統合する。
- **最上段は「要対応・期日一覧」＝網羅表示（2026-06-08 モック検討で確定）**:
  - 進捗率ヒーロー・要対応件数カードは**廃止**。
  - **思想（重要）**: 「今日やること」ではなく、**期日が来るもの・アラート予兆を網羅的に列挙し、教室長が「いつ Google カレンダーに入れるか」を判断する材料**にする。予定管理そのものは Google カレンダー側で行う前提。だからこの一覧は今日に絞らず、先の期日まで漏れなく拾うことが価値。
  - **期日帯でグルーピング**: 期限超過 / 今週 / 来週 / それ以降。期限超過は赤で強調。
  - 各行 = 種別バッジ＋期日＋「予定に追加」(カレンダー登録の入口)＋チェック(対応済みにする)。
  - 種別: 申込 / 振替 / 講習 / 面談 / フォロー / 手続き。要対応の各ソースから網羅生成する想定。
  - **未確定**: ①網羅対象として拾う期日・予兆のソース範囲 ②カレンダー連携の形（個別「予定に追加」/ 一括同期 / ICS 出力）。Google カレンダー連携は実装フェーズの検討事項。
- **最重要KPI（朝イチで見たい順）**:
  1. 本日のタスク（最上段）
  2. 未処理の申込・回答
  3. 本日の授業・出欠
  4. 要対応アラート
  → 講習進捗 [F] は最重要から外れたので、下部の折りたたみ扱いで良い。
- **経営指標の範囲（§2.5）**: 「軽い3つ＋中級」まで。
  - 採用: 在籍トレンド折れ線（昨年重ね）/ 増減ウォーターフォール / 退会率・継続率 / 退会ドリルダウン（学年・通学校別）/ 着地見込み。
  - **予算比をやる（在籍目標のみ）**: `school_targets` 新設＋目標入力UI。売上目標は今回外す。
  - **退会理由を記録する**: `students.withdrawal_reason` 追加＋退会時の選択UI。退会理由内訳を可視化。
  - 今回スコープ外: 売上・客単価（月謝定義が未確定のため後回し）、コホート継続率ヒートマップ、退会率アラート。

## 0. 目的

教室長（`manager` ロール）が「朝ログインしたらまずここを見れば、今日やるべきことと教室の状態が一目で分かる」状態を作る。
現状トップは `/students`（生徒名簿）にリダイレクトされ、教室運営の俯瞰ビューが無い。これを埋める。

- 想定ルート: `/home`（または `/dashboard`）。manager 以上はログイン後ここに着地。
- 権限: ページは manager / owner / admin に表示。teacher には出さない（teacher は `/today` 等へ）。
- 複数校対応: `getSelectedSchoolIds()` で選択中の教室スコープに連動。`'all'` 選択時は全校横断集計。

## 2. 各ブロックの中身

### [★] 業務の進捗ヒーロー（最重要）
教室長が朝イチで一番見たい「今日どれだけ捌けているか」。要対応タスクの総数と完了数を集計し、進捗率＋バーで大きく表示。

- 分子・分母: [B] の各対応種別の「処理済 / 全件」を合算（例: 新着回答の処理、振替確定、アラート対応）。
- 「未処理が0件」のときは達成感のある表示（全完了バッジ等）。
- 「進捗」を業務消化の意味で使う。講習の進捗率 [F] とは別物なので名称が衝突しないよう注意。
- データ: [B] 集約カードと同じソースを使い回す（二重集計を避ける）。

### [A] KPI サマリーカード
ヒーローの下に、補助的な数字を横並びで。各カードはクリックで該当ページへ遷移。

| カード | 数値 | データ元（既存関数） | 遷移先 | 優先 |
|--------|------|----------------------|--------|------|
| 未処理の申込 | 未リンク回答数 | `getRecentUnprocessedResponses()` | `/responses` | ◎ |
| 本日の授業 | 本日のコマ数 / 出欠未入力数 | `getScheduleEntries()` 当日分 + `attendance` | `/today` | ◎ |
| 要対応アラート | アラート件数 | `getAlertsLight()` の件数 | `/students`（アラート） | ◎ |
| 在籍生徒数 | active 生徒数 | `getStudents({ schoolIds })` の集計 | `/students` | ○ |
| 未読の連絡 | 掲示板未読数 | `bulletin.getUnreadCount()` | 掲示板へスクロール | ○ |

※ 件数系は軽量クエリを優先。重い集計は後追いロードで体感速度を確保。

### [B] 要対応 集約カード（件数バッジ）
**確定: 既存 Board の寄せ集めではなく、件数集約の新カード**として1枚に。「放置するとマズいもの」を優先度順に行として並べ、各行に件数バッジ＋遷移リンク。

| 行 | 件数ソース | 遷移先 |
|----|-----------|--------|
| 新着の未処理回答 | `getRecentUnprocessedResponses()` | `/responses` |
| 振替待機 | `PendingTransfersBoard` のデータ元 | `/schedule`（振替） |
| 申込期限が近い/超過 | `getAlertsLight()` 該当種別 | 該当申込 |
| 面談未実施・遅延 | `interviews` 由来アラート | 該当生徒 |

- このカードの「処理済 / 全件」を [★] ヒーローの進捗率に合算する。
- 各行クリックで詳細へ。0件の行は淡色 or 非表示。

### [C] 本日の授業 / 出欠状況
- 本日のコマ一覧（講師×時間帯×生徒）と、出欠の入力状況（未入力の強調）。
- データ: `getScheduleEntries()` 当日分 + `attendance`。`/today` ページのロジックを部分流用できるか確認。

### [D] 連絡掲示板
- 既存 `BulletinBoard` をそのまま配置。manager は投稿も可能。

### [E] アラート（軽量版）
- `getAlertsLight()` を使い、生徒ごとの注意（成績低下・面談遅延等）をコンパクト表示。
- クリックで該当生徒の詳細へ。重い `getAlertsHeavy()` は必要時のみ。

### [G] 経営指標 ＝ スナップショット（今この瞬間の構成）
教室の「現在の姿」を俯瞰するブロック。要対応[B]とは性質が違う（日々さばくものではなく、傾向を見るもの）。データ実在は調査済み。
→ 時系列・フロー（入退会の動き・昨対・予実）は別立てで §6 に詳述。

| 指標 | データ元 | 表示案 | 状態 |
|------|----------|--------|------|
| 学年構成 | `students.grade`（1〜13）＋ `getGradeCategory()` で小/中/高分類 | 横棒 or 積み上げバー（小中高×学年） | ✅ 即実装可 |
| 在籍状況 | `students.status`（active/inactive/withdrawn） | 在籍中・休会・退会の件数 | ✅ 即実装可 |
| 通学校別 | `students.school_name`（通う小中高名、NULL有） | 上位N校の生徒数ランキング | ✅ 即実装可 |
| 平均週回数 | `schedule_regular_patterns` の distinct `day_of_week` 件数 | 平均値＋週1/2/3/4/5以上の分布 | ✅ 即実装可 |
| 校舎別 | `students.school_id`（`'all'` 選択時のみ） | 校舎ごとの生徒数・平均週回数 | ✅ 即実装可 |
| **男女比** | **生徒の性別フィールドが存在しない** | 円グラフ/比率バー | ⚠️ **要マイグレーション** |

**男女比の前提作業（別タスク）**:
1. `students` に `gender`（`'male' | 'female' | 'other' | null`）カラム追加のマイグレーション。
2. 生徒編集フォームに性別入力欄を追加（既存生徒は未設定スタート）。
3. ダッシュボードは「未設定」を1区分として扱う。
→ 男女比だけは上記が完了するまで「準備中」表示 or 非表示にする。

**集計の置き場所**:
- 多くは取得済みの `getStudents({ schoolIds })` 結果を **フロントで groupBy** すれば足りる（新規エンドポイント不要）。
- 重くなる場合のみ、サーバー側に `getClassroomMetrics(schoolIds)` を新設して集計を寄せる。
- スコープは他ブロック同様 `getSelectedSchoolIds()` 連動。`'all'` のとき「校舎別」が活きる。

**表示位置**: 日次の[★][A][B]より下、[F]の近く。経営指標は「毎朝さばく」ものではないので最重要枠には入れない（折りたたみ or 別タブも検討）。

### [F] 講習・季節講習の進捗
- `CourseProgressDashboard` / 季節講習の `OperationsDashboard` への入口、もしくはサマリーのみ埋め込み。
- 通常時は折りたたみ、講習期間は展開をデフォルトにする等の出し分けも検討。

## 2.5 経営指標の発展 ＝ 時系列・フロー（§6 として詳述）

[G] が「今の構成（ストック）」なら、こちらは「動き（フロー）と基準比較」。経営判断に直結するのはこちら。
**設計思想**: ①件数より"動き"を、②件数より"率"を、③単独の数字より"昨対・予実"を見せる。

### データ前提（調査済み）
- **`student_logs`（`action='status_changed'`, `diff` jsonb, `created_at` index 付き）** が在籍/休会/退会の変更履歴を保持 → **過去の任意時点の在籍数を復元可能**。これが入退会トレンド・昨対比の基盤。
- 入会日 = 専用フィールド無し。`students.created_at`（または `student_logs` の `action='created'`）で代用。
- 退会日 = `students.withdrawal_date`（あり）。退会理由 = **無し**（欲しければフィールド＋入力UI追加）。
- 予算/目標 = **格納テーブル無し**。`school_targets`（仮）の新設が必要。
- グラフ = **recharts 3.7.0 導入済み**。トレンド/棒/エリアはそのまま描ける。

### 可視化メニュー（軽い→重い）
| ビジュアル | 何が分かる | データ | 投資対効果 |
|------------|-----------|--------|-----------|
| 在籍数トレンド折れ線（昨年ライン重ね） | 流れ＋昨対 | logs＋日付（既存） | ◎ 軽 |
| 増減ウォーターフォール（月初 +入会 −退会 ±休復 = 月末） | 増減の"なぜ" | logs（既存） | ◎ 軽 |
| 退会率・継続率 | 定着の健康度 | logs（既存） | ◎ 軽 |
| 退会ドリルダウン（学年別/通学校別にどこが抜けたか） | 打ち手の的 | logs＋student（既存） | ○ 中 |
| 予実ゲージ（目標在籍/売上の達成率） | 目標との距離 | **要 `school_targets` 新設** | ○ 中 |
| 着地見込み（純増ペースから期末を外挿） | 先手 | logs（既存）＋計算 | ○ 中 |
| コホート継続率ヒートマップ（入会月別の生存） | "いつ入った層"の定着 | logs（既存） | △ 重 |
| 退会率アラート（閾値超え・学年偏り検知） | 異常の早期発見 | logs（既存） | △ 重 |

### 「重さ」への方針（実装と運用は別物）
- **実装の重さ**: 「軽」3つ（トレンド/ウォーターフォール/退会率）は新テーブル不要・recharts流用で最優先。
- **運用の重さ（より重要）**:
  - logs ベースの指標は **入力の手間ゼロ**（自動記録）→ 運用が回り続ける。これを主軸に。
  - 予実比は **毎月の目標入力運用** が前提。続かないと指標が死ぬ → 目標は「年度頭に12ヶ月分一括入力」等で入力を最小化。
  - 退会理由は今フィールド無し → 出すなら「退会時に理由選択」の一手間とのトレードオフ。
- **クエリの重さ対策**: logs 毎回フルスキャンが重ければ、**月末在籍数の月次スナップショット表**で確定保存（過去が安定・高速化）。ただしバッチ運用増。まずは都度集計で開始し、重くなったら導入。

### 売上・予実の留意（要ビジネス定義）
- 請求 `billing_*` テーブルはあるが、生徒向け**月謝/単価マスタは無い**（金額は手入力/同期想定）。
- 「月謝の定義」「在籍の定義（active のみ / inactive 含む）」「目標の粒度（教室全体/学年別）」を確定しないと売上・予実は組めない。§4 の論点に追加。

## 3. データ取得方針

- すべて `getSelectedSchoolIds()` のスコープを渡す（複数校 `.in()` 対応済み関数を使用）。
- 時系列集計（在籍トレンド・昨対・退会率）は新規 `src/lib/api/dashboard.ts` に `getEnrollmentTrend(schoolIds, range)` 等を集約。
- 初期表示は **軽量・件数系を先に**、重い集計（進捗・出欠詳細）は遅延ロードして体感速度を確保。
- 既存の `AuthContext` / `MasterDataContext` から profile・schools・selectedSchoolId を取得。
- 可能な限り **既存 API 関数を再利用**し、新規の集計エンドポイントは最小限に。
