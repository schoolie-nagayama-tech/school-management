# 生徒ハブ（生徒詳細のページ化）実装計画

作成: 2026-09-28 ／ 状態: **第1段 実装中**
モック: `public/student-hub-mock.html`（PR #262）。見た目と並び順の正典はモック。

---

## 0. 何をするか

生徒詳細は URL を持たないモーダルで、5タブに収まらず、面談ページと表示が重複し、
生徒の情報が12のサブルートに散らばっている。根は「URLを持たないこと」ひとつなので、
**`/students/[studentId]` に、生徒1人の情報を集めたページ（生徒ハブ）を作る。**

## 1. 権限と入口（2026-09-28 ユーザー決定）

**教室長以上だけの変更にする。講師の画面は今のまま一切変えない。**

|                                            | 講師                       | 教室長以上                           |
| ------------------------------------------ | -------------------------- | ------------------------------------ |
| 生徒ハブ `/students/[studentId]`           | 開けない（生徒一覧へ戻す） | 開ける                               |
| 生徒一覧で名前を押す                       | 今のモーダル               | **ハブへ直行**                       |
| 座席表・入会申込・請求・講習進行表から開く | 今のモーダル               | 今のモーダル＋「ページで開く」リンク |

- 判定は `src/lib/utils/roles.ts` の `isManagerOrAbove`。画面ごとに role を直書きしない。
- **これは画面の出し分けで、データの守りではない。** 講師は今も成績・面談記録を読める
  権限（`ROLE_PERMISSIONS`）とRLSを持っている。今回の目的は「講師の画面を変えないこと」。
- `/students/[studentId]` というページは今まで存在しなかった（サブルートだけ）ので、
  追加しても講師が使っている画面は壊れない。

## 2. 作りの方針

- **既存の型に従う**: `'use client'` ＋ `useParams` ＋ `AdminLayout`。
  この階層にサーバー側の事前取得の型は無い（`docs/perf-students-top-section-plan.md`）。
- **セクションは見えてから読み込む。** 16セクションが一斉にデータを取りに行くと、
  生徒管理ページで起きた「同時リクエストで接続プールが飽和する」事故を繰り返す。
  各セクションは画面に近づくまで枠だけ出し、IntersectionObserver で近づいたら取得を始める。
  先頭の 今の状態・基本情報・気にすること・通塾日程 だけは最初から読む。
- **既存の部品を使う。** 生徒IDを渡せば自分で取得する部品はそのまま置く。
  同じデータを別実装で描き直さない（成績サマリは既に4か所で別実装になっている）。
- **ヘッダーは固定、ほかは固定しない。** 右カラムを sticky にしたらスクロールが
  連動しないと不評だった（モック検討時）。

### 注意すること（2026-09-28 ユーザー決定の A案で第1段に入れた）

生徒1人で引く集計は作らず、**既存の教室単位のアラート計算を生徒の教室1つで回し、この生徒の分を抜き出す。**

- 取得は生徒一覧のアラート欄（`AlertBoard`）と同じ順: Light を先に出し、Heavy は `whenNetworkIdle()` の後。
  `mergeStudentAlerts` で結合する。
- 教室は**生徒の所属1つ**（選択中の教室が「すべて」でも）。1教室のほうが軽く、選択中が1教室なら
  一覧と同じキャッシュキー（`cacheKey` ＝教室IDを並べ替えて連結）になる。
  ★一覧の Light はサーバーで先取り（クライアントのキャッシュに書かない）ので、効くのは Heavy のキャッシュ
  （一覧で Heavy を取り終えてから15秒以内に開いたとき）。
- 絞り方は `src/lib/alerts/studentAttention.ts` に集めた。ロールで外す種別（`alertTypesHiddenForRole`）は
  `AlertBoard` も同じ関数を使う。ハブではさらに 面談更新（講師向けの良い知らせ）と
  未完了タスク（隣の「未完了の約束」と二重）を外す。種別の有効・無効としきい値（アラート設定）は
  計算の中で効いている。
- 並びは生徒一覧の生徒カードと同じ（重要度の高い系列から）。各行は `AlertItem`（飛び先・対応済みが一覧と同じ）。

### 今の状態（2026-09-28 第1段に入れた）

「一番目に入る左上が使えていない」（注意も約束も無い生徒で「ありません」が2行出るだけで、右の基本情報のほうが長く、
左の下が空く）というユーザー指摘で、第2段から繰り上げた。上部の左カラムを **今の状態 → 気にすること** の縦積みにする。

新しい集計は作らず、**下のセクションと同じ関数で数える**（上の指標と下の表の数字を食い違わせない）。
組み立ては純粋関数 `src/components/students/hub/hubStatus.ts`（テスト `src/__tests__/components/hubStatus.test.ts`）。

| 指標                | 表示                                | 数え方                                                                                                                                    |
| ------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 次回授業（2月から） | `9/30(水) 19:00`／`数学・田中`      | `getStudentScheduleEntries`（今日〜60日先）。取消・振替元・今日の開始時刻を過ぎたコマを除く                                               |
| 直近の定期テスト    | 5科合計／前回比／`日付 テスト名`    | `computeScoreSummary` に5科だけ渡す（実技が入る学校で9科合計にしないため）。5科に欠けがあれば「一部未入力」、前回に欠けがあれば前回比なし |
| 前回の面談          | `92日前`／`日付 種別`               | `interview_type !== 'task'` の最新。経過日数は `daysSince`                                                                                |
| 今月の宿題・遅刻    | `宿題 3回・遅刻 1回`                | `computeDisciplineMonthly` の今月分（日単位）。記録があって両方0なら「なし」                                                              |
| 進行表              | `4冊中 1冊が停滞`（停滞があれば黄） | 管理中のテキスト × `summarizeTextbookProgress` の停滞（最終指導から14日超）。取得は `whenNetworkIdle` の後                                |
| 講習                | `2026 冬期講習`／`提案書 下書き`    | `getProposalsByStudent`＋`getKoushuEnrollmentsByStudent` → `groupStudentKoushu` の先頭の期（講習欄の一番上と同じ）                        |

- 値が無いときは「—」と短い理由（「予定なし」「記録なし」）。空欄や「0回」の羅列にしない。
- 色は対応が要るもの（停滞）だけ。赤は使わない（赤は注意することのアラートが担う）。
- **取得は共有する**（`HubDataContext`）: 成績・面談記録・宿題遅刻のセッション・進行表は、今の状態と下のセクション
  （成績・志望校・気にすることの未完了の約束・進行表・宿題遅刻）が1回の取得を共有する。
  二重に取るのは、自分で取る既存部品と重なる2か所だけ: 講習（`StudentKoushuTab`）と面談記録（`InterviewList`）。
  どちらも見えてから読み込む位置にあるので、開いた直後には重ならない。授業予定は予定表の部品と範囲が違う（表示中の月）ので別に取る。
- 気にすることは、注意すること（Light・Heavy とも読み終えて0件）と未完了の約束（0件）が両方空なら1行に畳む。

## 4. 間違えやすいこと（モック検討で確かめた事実）

- **NESTに列が無いものは出さない**: 生年月日・住所・電話・メール・保護者氏名・入会日・
  請求の金額・志望校の判定。問合せ記録にある保護者の連絡先も出さない（ユーザー判断）。
- **担当講師の正典は座席表**（`schedule_entries.teacher_id`）。`fixed_teacher_ids` は希望。
- **予定表は教室で絞らない。** 他教室の振替・講習もその生徒の予定（#196 の判断）。
- **表の赤はアラートと同じ閾値**: 定期テストは前回から10点以上、模試は偏差値5以上の下落。
- **「2月から」**: 座席表か保護者アカウントが要る表示には枠線だけのタグを付ける
  （担当・次回授業・保護者との連絡・予定表・出欠・保護者セクション）。
- **未ページングの `.select()` は1000行で静かに切れる。** 新設する取得関数は生徒で絞る。
