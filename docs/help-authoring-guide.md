# ヘルプの書き方（機能を足したとき・変えたとき）

機能を変えたら、**同じPRの中で**ヘルプも直す。あとでまとめて直すことにすると必ず置いていかれる。

ヘルプの本文（`src/lib/help/faqData.ts`）は、画面に出る説明であると同時に、**AIヘルプが答えを作るための唯一の材料**でもある。ここに書いていないことをAIは答えない（黙って `unanswered` にする）。逆に、実装と違うことが書いてあると、AIはそれを疑わずに自信たっぷりに案内する。**間違ったヘルプは、無いヘルプより悪い。**

- 正典（設計の経緯・なぜこうなっているか）: [ai-help-plan.md](ai-help-plan.md)
- 本文: `src/lib/help/faqData.ts`（160項目 / 15カテゴリ）
- 索引とプロンプト: `src/lib/help/faqIndex.ts`, `src/lib/help/aiHelpPrompts.ts`
- テスト: `src/__tests__/lib/faqIndex.test.ts`

---

## 1. 変更の種類ごとに、どこを直すか

| やったこと                     | 直す場所                                                            |
| ------------------------------ | ------------------------------------------------------------------- |
| 画面・ボタン・手順が変わった   | 該当項目の `answer` / `path` / `steps` / `tips`                     |
| 画面や機能が増えた             | 該当カテゴリに項目を1つ追加（画面があるなら `link` も）             |
| 運用の決まりが増えた・変わった | `rules`（§3。ここが一番効く）                                       |
| 呼び名・用語が変わった         | `GLOSSARY_DATA` と、各項目の `keywords`                             |
| 誰が使えるかが変わった         | `roles`（権限）                                                     |
| まだ公開しない／試作で出す     | `status` + `statusNote`（§4）。**`roles` で隠さない**               |
| 機能を消した                   | 項目ごと消す。他項目の `related` からも消す（残すとテストが落ちる） |
| その画面でよくやる操作を足した | そのページの `ContextHelp` の `topics`                              |
| ロール別の入口を変えたい       | `src/lib/help/exampleQuestions.ts`（質問の例のチップ）              |

## 2. 1項目の書き方

```ts
{
  question: 'CSV一括インポートの手順',
  answer: 'CSVファイルから複数の生徒を一括で登録できます。…',
  path: 'ヘッダー「生徒管理」→ 生徒一覧ページ',
  steps: ['…', '…'],
  tips: ['…'],
  keywords: ['CSV', 'インポート', '一括'],
  link: { href: '/students', label: '生徒一覧を開く' },
  roles: ['admin', 'manager'],
  related: ['生徒の新規登録方法'],
}
```

**`question`** — 困っている人が打つ言葉で書く。機能の正式名称を並べても、その名前にたどり着けなくて困っている人には手がかりにならない。
★これが項目のID（`faqItemId`）の元になる。**書き換えるとIDが変わる**ため、`help_questions.matched_ids` に残っている過去の記録が別物を指すようになる。表記ゆれを拾いたいだけなら `question` を変えず `keywords` に足す。

**`answer`** — 2〜4文。まず結論。AIはここを土台に答えを組み立てる。

**`path`** — 「ヘッダー「◯◯」→ ◯◯ページ」の形。**画面に出ているラベルをそのまま写す**。1字でも違うと探せない。

**`steps`** — AIは手順を**そのまま写す**（言い換えない・省かない・順番を変えない、とプロンプトで固定してある）。だからボタン名は実物どおりに書く。「講師には表示されません」のような条件は、その手順の文中に入れる。

**`tips`** — つまずきどころ・例外・やってはいけないこと。「◯◯の欄はありません」のような**無いことの明記**もここ。無いものを探して詰まる人が多い。

**`keywords`** — ★検索の対象は `question` / `answer` / `keywords` だけ（AIが使えないときの受け皿は加えて `rules` も見る）。**`steps` や `tips` の中にしかない語では引けない。** 手順の中にしか出てこない重要語（画面名・ボタン名・現場の呼び名）は `keywords` に上げる。

**`roles`** — 「公開されたときに誰が使う機能か」（権限）だけを表す。省略＝全員に見せる。
★`filterIndexByRole` は**AIに渡す前に見出しごと落とす**。`roles` を付けた項目は、それ以外のロールからは存在自体が見えない（「権限がありません」ではなく「載っていません」になる）。

**`link`** — 実際に開ける画面があるときだけ。AIの回答にボタンとして出る。

**`related`** — 相手の `question` を**完全一致**で書く。リンク切れはテストが落とす。

## 3. 規則（`rules`）— 具体値に当てはめてよい唯一の場所

AIは本文を要約して答えるだけで、**自分で推論はしない**。「9月請求分って何月分？」のような当てはめは、規則を書いておかない限り答えられない（一般常識で補うことは禁じてある。塾業界の慣習で勝手に埋められると事故になるため）。

そこで、**当てはめてよい対象をデータ側で限定した**のが `rules`。`steps` とは別枠で、AIは規則に限って利用者の具体的な値に当てはめてよく、そのとき**使った規則を必ず答えの1文目に書く**（前提が違っていれば読んだ人が気づけるように）。

```ts
rules: [
  '月謝は翌月分を当月に請求する先取り運用。「◯年◯月請求」は、その翌月に実施する授業の分を指す（2026年9月請求＝2026年10月分）',
],
```

> 質問「12月請求分って何月分？」
> 回答「月謝は翌月分を当月に請求する決まりなので、12月請求分は翌年1月に実施する授業の分です。」

**書くもの**

- 人によって答えが変わる前提（「◯◯って何のこと？」が現場で毎回聞かれるもの）
- 計算・読み替えが要る決まり（何月分・何コマ・どの単位で数えるか）
- 自動でこうなる／ならないの境目（「◯◯は自動で翌月にならない」など、例外側も書く）

**書かないもの**

- 操作手順（`steps` へ）／つまずき（`tips` へ）
- 実装の都合そのもの。読むのは講師と教室長で、DBの話は要らない

**書き方**

- 1件1文。条件と結論を1文に収める（AIが分割して誤読しない）
- 具体例を括弧で1つ添える。当てはめの型が伝わる
- ★**書いていない規則は当てはめられない。** 運用の前提が増えたらここに足す。それをしない限りAIは黙る（黙るのは仕様どおりで、勝手に埋めるより望ましい）

現在7項目に明文化済み（請求の何月分・タスクの共有単位・学年一括更新の副作用・テスト目標の粒度・出勤簿の状態遷移・アラートの重さ優先・自動紐付けの条件）。

## 4. まだ公開しない機能をどう書くか

実装は入ったが利用者にはまだ出さない、というものは `status` で表す。

```ts
status: 'planned',
statusNote: '2027年2月の保護者ポータル公開に合わせて開放予定。いまは画面を開けません',
```

| 値               | 意味                                               |
| ---------------- | -------------------------------------------------- |
| `live`（省略時） | 公開済み。権限があればいま使える                   |
| `preview`        | 実装済みだが試作。限られた入口・限られたロールだけ |
| `planned`        | 実装済みだが公開前。いまは使えない                 |

- ★**`roles: ['admin']` で隠さない。** roles はAIに渡す前に落とすので、隠すと下位ロールには「載っていません」としか答えられなくなる（実際にこれで問合せ管理26項目が教室長から全滅していた）。未公開でも候補には残し、「まだ使えません」と**答えさせる**のが正しい。
- `status` が `live` でない項目には `statusNote` が必須（テストで強制）。誰がどこから触れるか、いつ公開かを一言で。
- 本文（`answer` / `steps`）は**公開後の正しい内容を今のうちに書いておく**。AIは公開状態を1文目に断ったうえで手順も案内する（いつ何ができるようになるか知りたい人がいるため）。
- **公開したら `status` と `statusNote` を消すだけ。** 本文は触らなくてよい。

## 5. 用語集（`GLOSSARY_DATA`）

回答のたびに**全文がAIに渡る**（現在16語・約2,300字）。増やしすぎると毎回のコストになるので、**現場の呼び名と画面の言葉がずれている語**だけに絞る。

- 書くのは読み替えだけ。★操作手順を書かない（用語集から手順を作らない、とプロンプトで禁じてある）
- 数え方・単位のずれ（「コマ」「週回数」など事故の元）はここに1行あると効く

## 6. 画面内ヘルプと質問の例

**`ContextHelp`**（設置済み9ページ）— そのページでよくやる操作を2〜4件。`title` / `description` / `steps`（2〜4手順）。ページ内から質問すると、そのページのパスがAIに渡り、対応する項目が先頭に寄る（`prioritizeByPath`）。

**`exampleQuestions.ts`**（入力欄の下のチップ）— 押した1回目が外れると二度と使われないので、**必ず当たる例だけ**を置く。

- 見出しをそのまま並べない（それではキーワード検索と同じで、普通の言葉で聞いていいことが伝わらない）
- 未公開・試作の機能を置かない（「まだ使えません」で終わり、最初の一歩にならない）
- ★そのロールから**見える**項目に当たるものだけ。特に `all`（ロール未確定）では、ロール指定のない19項目しか見えない
- チップが必ず当たることはテストで固定してある。チップを足したら `npx vitest run src/__tests__/lib/faqIndex.test.ts`

## 7. 出す前のチェック

```bash
npx vitest run src/__tests__/lib/faqIndex.test.ts
```

テストが見てくれるのは、ID衝突・`related` のリンク切れ・`statusNote` の付け忘れ・チップが当たるか、まで。**実装と合っているかは人間が見るしかない。**

- [ ] その画面を実際に開いて、`path` とボタン名を突き合わせた
- [ ] 存在しない画面・ボタン・設定を書いていない（消えた機能の説明が残っていないか）
- [ ] `roles`（権限）と `status`（公開状態）を混ぜていない
- [ ] 未公開なら `statusNote` を書いた
- [ ] 手順の中にしかない重要語を `keywords` に上げた
- [ ] 運用の前提を増やしたなら `rules` に書いた
- [ ] 消した項目を他の `related` から外した

## 8. 出したあと

`/help` の**「答えられなかった質問」**（システム管理者のみ表示・AIヘルプの直下）を定期的に見る。ここに溜まるのは、利用者が実際に打った言葉で、FAQに無かったものそのもの。**この機能の価値はここでしか出ない。**

- `unanswered` が続く質問 → FAQ項目が足りない。§2 に戻って書き足す
- 同じことを言い換えて何度も聞かれている → 言葉が届いていない。`keywords` を足すか `question` を利用者の言い方に寄せる（IDが変わる点は §2 参照）
- 「当てはめ」に失敗している → `rules` が足りない
