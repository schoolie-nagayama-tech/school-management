正典。保護者ポータルを「バージョン2」としてクローズド開発で再構築するための要件定義。

- ステータス: 要件確定（2026-07-14 起票）

## 1. 目的とゴール

**現在 Grow（やる気スイッチ系アプリ）で行っている保護者との双方向のやり取りを本アプリに置換し、UXを向上させる。**

### 完了の定義（Grow 置換マトリクス）

Grow で使っている機能がすべて v2 で代替できたら置換完了。これが最終ゴール。

| # | Grow の機能 | v2 での受け皿 | ドメイン | 実装段 |
|---|---|---|---|---|
| G1 | 個別メッセージ（チャット） | ④ 1対1チャット（教室宛1本・生徒ごとスレッド） | C | Stage 2 |
| G2 | 教室からのお知らせ配信 | ⑤ 掲示板拡張（audience=保護者/生徒、全体/学年/個別） | C | Stage 2 |
| G3 | 面談調整（一斉配信→Googleカレンダー予約） | 当面: お知らせ配信に予約URLを掲載（G2 で代替可）。将来: 面談/体験セルフ予約（INQ予約系）をログイン文脈に接続 | C→S | Stage 2（暫定）/ Stage 3（本実装） |
| G4 | 授業スケジュール閲覧 | 時間割・今後の予定ビュー（紐付け生徒の schedule_entries） | S | Stage 3 |
| G5 | 欠席・遅刻連絡 | 欠席連絡 専用導線（時限選択→欠席/遅刻/振替希望→教室受付） | S | Stage 3 |

## 3. スコープ

### 対象ユーザー
- **保護者**（invite_type=guardian）: 紐付け生徒の全ポータル情報を閲覧・発信できる。
- **生徒本人**（invite_type=student, relation=self）: 自分の情報のみ。**保護者向け情報（面談調整等）は出さない**。
- スタッフ側は既存 user_profiles / Supabase Auth のまま（主体分離。変更しない）。

### 出さないもの（確定済みの再掲）
- **請求・支払い**（別管理）。
- 保護者の PII（住所・電話・メール）は portal_accounts に持たない（別システムが正）。

### v1（既存 `/portal/[schoolCode]/`）との関係
- v1 は公開フォーム集（moshi/mogi/shukaisu/soudan/youbi/zoukoma ＋ 擬似認証 student-dashboard）。
- **v2 開発中、v1 には一切触れない**。運用も v1 で継続。
- フォーム機能は Stage 3 で v2 に取り込む（回答を本人/紐付け生徒スコープに）。取り込み時に「v1 の UI をそのまま生かすか、v2 デザインに寄せるか」を判断する。
- v1 の廃止・リダイレクトは v2 公開後の課題（本書のスコープ外。M2 以降に判断）。

## 4. 機能要件（ドメイン別）

詳細設計は `account-line-design.md` §9 と roadmap P3 の記述が正。ここでは v2 として作る「原型」の到達点だけ定義する。
方針: **各機能はまず原型（動く最小形）まで作り、作り込みは動かしながら行う。**

### 0. マイページ（器）
- ログイン後のホーム。紐付け生徒の切替（兄弟）、各ドメインへの導線、新着バッジ。
- 掲載項目（確定済み）: 時間割・今後の予定 / 出欠サマリ / 授業報告書 / 宿題（報告書から拾う）。
- 原型 = ログイン→自分の紐付け生徒の基本情報と各機能への入口が出る状態。

### C. コミュニケーション（Grow 置換の核・最初の機能ドメイン）
- **④ 1対1チャット**: chat_threads / participants / messages / reads。相手は教室（室長）宛1本、スレッドは生徒ごと。スタッフ側の受信・返信 UI も対で作る（教室側が返せないと双方向にならない）。
- **⑤ 掲示板拡張**: 既存 BulletinBoard に audience（社内/保護者/生徒・複数可・既定=社内）＋配信単位（全体/学年/個別）。portal 側既読は reader_kind or 専用テーブル。
- **面談調整（暫定）**: お知らせに URL を貼れれば Google カレンダー予約リンクの配信で Grow の現運用を代替できる。専用機能は作らない。
- 原型 = 保護者⇔教室でメッセージが往復し、教室からのお知らせが対象保護者にだけ見える状態。

### S. スケジュール
- 時間割・今後の予定ビュー（schedule_entries、種別凡例付き）。
- 欠席連絡 専用導線（保護者発信→教室受付。座席表・振替フローとの本連動は作り込み段階で）。
- v1 フォーム群の取り込み（擬似認証→本物アカウント、回答スコープ化）。
- 面談/体験セルフ予約（INQ予約系）のログイン文脈接続。
- 原型 = 紐付け生徒の予定が見え、欠席連絡が教室に届く状態。

### R. 報告書（最後の段）
- 保護者ビュー = P1-14 報告書×進行表マージの「ビュー2」。**P1-14 が未着手のため依存あり**。
- 公開承認ワークフロー: 講師下書き→室長承認→公開。承認前は保護者非表示。
- 原型 = 承認済み報告書が保護者に一覧・閲覧できる状態（マージ完成を待たず、既存報告書データの読み取りビューから始めることを許容する）。

### 横断: 通知
- 最終形は確定済みの通知マトリクス（LINE push 一本。届ける=push／見れば済む=画面0円）。
- **クローズド期間は画面内新着表示のみ**（マイページのバッジ＋一覧の未読）。
- 実装は通知イベントを1箇所に集約し（notification dispatcher）、チャネル（画面内/LINE/メール）を差し替え可能にしておく。LINE 取得後に push チャネルを足すだけで済む構造にする。

## 5. 正典（account-line-design.md）からの変更点

基本は引き継ぎ。変えるのは以下だけ。

1. **実装着手を LINE 取得後としない → ID/PW 先行で今すぐ着手**
   - 正典は「実装はLINE取得後」としていたが、LINE取得（P1-0）は進捗ゼロのクリティカルパス。待つと土台開発が止まる。
   - portal_accounts は元々 login_id/password_hash を持つ設計なので、**ID/PW ログインだけで全機能が成立**する。LINE ログイン・LINE push は取得後に同じセッションへ着地させる（案3の利点）。
   - クローズド期間（アドミンのみ）は ID/PW で全機能検証できる。
2. **クローズド開発方式の追加**（§6。正典に無かった v2 固有の要件）
3. **通知はクローズド期間中、画面内のみ**（G7。正典の「LINEプッシュ一本」は最終形として維持）
4. **面談調整は当面お知らせ配信で代替**（G3。専用のセルフ予約接続は Stage 3）
5. **報告書の原型は P1-14 完成を待たない**（既存データの読み取りビュー先行を許容）

認証方式（案3: 自前ログイン→Supabase互換JWT→RLS）、データモデル（portal_*）、権限（invite_type）、失効（withdrawal_date 超過で自動失効）、チャット/掲示板のスキーマ案、通知マトリクス、コストモデルは**すべて正典のまま**。

## 6. クローズド開発方式（v2 固有）

### 6-1. ルート・コード分離
- 新領域は **`/mypage`**（ログイン制なので v1 と違い schoolCode 不要）。恒久名を最初から使い、公開時のリネーム churn を避ける。
- ログイン画面は `/mypage/login`、招待受諾は `/mypage/invite/[token]` を想定。
- 既存 `/portal/` 配下のファイルは変更しない。共有したいコンポーネントは移動せず import 参照のみ（v1 に影響を出さない）。

### 6-2. アクセス制御（クローズドの担保）
二段構え。
- **(a) 招待制**: portal_invitations の発行 UI・API を**アドミン限定**にする。招待が無ければ誰もアカウントを作れない＝構造的にクローズド。
- **(b) 全体スイッチ**: system_settings にポータル有効フラグ（例 `portal_v2_enabled`、既定 OFF）。OFF なら `/mypage` 全体を 404/準備中に。緊急遮断用。
- 公開段階での教室単位 ON/OFF は school_widget_settings 同型で後から足す（今は作らない）。

### 6-3. DB 分離度（不変条件）
- **追加するのは portal_*・chat_*・通知系の新テーブルのみ。既存テーブルのスキーマは原則変更しない。**
  - 例外は掲示板拡張（audience 列等）のみ。既定値=社内で既存動作を変えないこと。
- 既存テーブル（students / schedule_entries / 報告書等）へは**ポータル用 RLS ポリシーの追加**のみ（スタッフ用と併存）。既存ポリシーは触らない。
- **ポータルJWTは専用Postgresロール `portal` で発行する（2026-07-14 決定・本番PoC済み）**。
  - 理由: `authenticated` で発行すると「authenticated＝スタッフ」前提の既存の広いポリシー（subjects/curriculum_items/textbooks の全開放等）が保護者にも適用されてしまう。専用ロールなら**デフォルト全拒否**で、将来テーブルが増えても自動的に安全側。
  - 帰結: ポータルに見せるテーブルは今後も**明示的な `grant ... to portal` ＋ `to portal` ポリシー**が必要。忘れると見えないだけ（安全側に倒れる）。
  - 技術メモ: `auth` スキーマは portal に usage 付与不可（Supabase内部所有）のため、ポリシーでは `auth.uid()` でなく `public.portal_uid()`（request.jwt.claims から sub を読む自前関数）を使う。
- RLS 回帰テスト（既存 CI）にポータル用ポリシーのケース＋デフォルト拒否（portal で subjects 等が読めない）のケースを追加する。

### 6-4. 検証データ
- まず **is_test 生徒＋ダミーのポータルアカウント**で全機能を通す。
- 実在生徒データへの接続は読み取り系（スケジュール閲覧・報告書）から。書き込み系（チャット・欠席連絡）はアドミン自身のテスト運用で確認してから。
- 個人情報を新しい経路（ポータル JWT）に流す前に、RLS 境界テスト（自分の紐付け生徒のみ読める／他生徒は弾かれる／失効後は見えない）を必ず先に通す。

## 7-2. Stage 2 詳細仕様（2026-07-14 確定・UIモック承認済み）

UIモックで合意した設計。実装の契約。

### チャット（生徒ごと1スレッド・相手＝教室）
- テーブル: `chat_threads`(school_id/student_id/created_by/created_at, student_idにunique) / `chat_thread_participants`(thread_id/portal_account_id) / `chat_messages`(thread_id/**sender_kind: 'staff'|'portal'|'system'**/sender_id nullable/body/**template_kind** text nullable/**payload** jsonb nullable/created_at) / `chat_reads`(thread_id/reader_kind/reader_id/last_read_at)。
- **単一スレッド維持**。混乱回避は (a)話題フィルタ（すべて/欠席・振替/面談 = template_kind で絞る）(b)テンプレの構造化カード表示。多スレッドは作らない。
- 保護者からの初回送信でスレッド自動作成。相手は教室（室長）1本、講師個別宛にしない。
- スタッフ側UI（室長の受信箱・返信）も対で作る。

### テンプレ（構造化メッセージ）
- 種別 `template_kind`: `absence`(欠席・遅刻) / `transfer_request`(振替希望) / `meeting_request`(面談希望)。payload に日付・時限・理由・振替希望等を持つ。
- 保護者はクイックアクションから小フォームで送信 → payload 付き chat_message として投稿。
- **振替ルール（2026-07-14 追加確定）**:
  - **締切: 対象授業の前日 21:00（JST）まで**。締切後〜当日は振替不可＝**欠席のみ**受け付ける。UIで振替希望を無効化（理由表示）し、**サーバー側でも必ず検証**（クライアント改ざん対策）。
  - **振替希望時は希望日時を第1〜第3希望まで入力**（第1必須、第2・第3も入力を促す）。payload に `candidates: [{date, slot}...]` として保持し、構造化カードに第1〜第3希望を表示。教室はその中から座席表で組む。
  - 受付の自動返信は締切判定を文面に反映（例: 締切内=「希望日時を確認し、振替日が決まり次第ご案内します」／当日=「当日のご連絡のため欠席として承りました（振替対象外）」）。

### 自動生成メッセージ（sender_kind='system'）★今回の追加要件
- **受付の自動返信**: 保護者が absence/transfer_request を送ると、**payloadの実日付を当てはめた受付メッセージをシステムが即時自動投稿**（室長は手打ち不要）。文面はサーバーで生成。
- **振替確定の座席表からの自動発信**: 座席表で振替コマを組んで確定した瞬間（`src/lib/api/schedule.ts` の `completeHeldTransfer`、既に `transfer_notifications` へpending行をINSERTしている箇所）をフックに、**実際の振替日・時限・科目を当てはめたシステムメッセージを保護者スレッドへ自動投稿**。
  - フック方式: `completeHeldTransfer` 成功後にクライアントから新設サーバールート（例 `POST /api/mypage/chat/system/transfer`、requireManager）を叩く。サーバーは service role で該当生徒の紐付け保護者アカウント→スレッドを解決し system メッセージ投稿＋メール送信。**紐付け保護者が居なければ no-op**（クローズド期間の大半の生徒はポータル未登録なので静かにスキップ）。座席表本体への変更は「成功後に1関数呼ぶ」だけに留め、失敗しても振替登録は成功扱い（非致命）。
  - 冪等性: `transfer_notifications.id` または toEntry.id をキーに二重投稿を防ぐ。

### 掲示板 audience 拡張（唯一の既存テーブル変更）
- `bulletin_posts` に列追加: `audience text[]`（既定 `{社内}`）/ `target_scope text`（'all'|'grade'|'individual', 既定'all'）/ `target_grade int[]`（学年指定用）。個別指定は別テーブル `bulletin_post_targets`(post_id/student_id)。
- **既定 `{社内}` で既存投稿・既存動作は完全不変**。保護者に出すには明示選択。
- ポータル既読は既存 `bulletin_reads`（スタッフ前提）を汚さず別テーブル `bulletin_portal_reads`(post_id/portal_account_id/read_at)。
- ポータル用RLS: `portal` ロールに `grant select on bulletin_posts` ＋ audience に保護者/生徒を含み、かつ target_scope に応じて（all / 自分の紐付け生徒の学年 / bulletin_post_targets に自分の紐付け生徒）該当する投稿のみ可視。

### メール通知（③の追加要件）
- クローズド期間の通知は画面内バッジ＋**メール**（当初は画面内のみとしていたが、メール通知も付ける方針に変更）。
- 既存 Resend 基盤に相乗り（`send-inquiry-mail` と同型の Edge Function か、既存の送信経路を再利用）。チャット新着・お知らせ配信・自動メッセージで送る。
- 通知は1箇所のディスパッチャに集約し、チャネル（画面内/メール/将来LINE）を差し替え可能に。

### 検証
