**現在 Grow（やる気スイッチ系アプリ）で行っている保護者との双方向のやり取りを本アプリに置換し、UXを向上させる。**

Grow で使っている機能がすべて v2 で代替できたら置換完了。これが最終ゴール。

## 3. スコープ

### 対象ユーザー

- **保護者**（invite_type=guardian）: 紐付け生徒の全ポータル情報を閲覧・発信できる。
- **生徒本人**（invite_type=student, relation=self）: 自分の情報のみ。**保護者向け情報（面談調整等）は出さない**。
- スタッフ側は既存 user_profiles / Supabase Auth のまま（主体分離。変更しない）。

### 出さないもの（確定済みの再掲）

- **請求・支払い**（別管理）。
- 保護者の PII（住所・電話・メール）は portal_accounts に持たない（別システムが正）。

### v1（既存 `/portal/[schoolCode]/`）との関係

- v1 は公開フォーム集（moshi/mogi/shukaisu/soudan/youbi/zoukoma ＋ 擬似認証 student-dashboard）。
- **v2 開発中、v1 には一切触れない**。運用も v1 で継続。
- フォーム機能は Stage 3 で v2 に取り込む（回答を本人/紐付け生徒スコープに）。取り込み時に「v1 の UI をそのまま生かすか、v2 デザインに寄せるか」を判断する。
- v1 の廃止・リダイレクトは v2 公開後の課題（本書のスコープ外。M2 以降に判断）。

## 4. 機能要件（ドメイン別）

詳細設計は `account-line-design.md` §9 と roadmap P3 の記述が正。ここでは v2 として作る「原型」の到達点だけ定義する。
方針: **各機能はまず原型（動く最小形）まで作り、作り込みは動かしながら行う。**

### 0. マイページ（器）

- ログイン後のホーム。紐付け生徒の切替（兄弟）、各ドメインへの導線、新着バッジ。
- 掲載項目（確定済み）: 時間割・今後の予定 / 出欠サマリ / 授業報告書 / 宿題（報告書から拾う）。
- 原型 = ログイン→自分の紐付け生徒の基本情報と各機能への入口が出る状態。

### C. コミュニケーション（Grow 置換の核・最初の機能ドメイン）

- **④ 1対1チャット**: chat_threads / participants / messages / reads。相手は教室（室長）宛1本、スレッドは生徒ごと。スタッフ側の受信・返信 UI も対で作る（教室側が返せないと双方向にならない）。
- **⑤ 掲示板拡張**: 既存 BulletinBoard に audience（社内/保護者/生徒・複数可・既定=社内）＋配信単位（全体/学年/個別）。portal 側既読は reader_kind or 専用テーブル。
- **面談調整（暫定）**: お知らせに URL を貼れれば Google カレンダー予約リンクの配信で Grow の現運用を代替できる。専用機能は作らない。
- 原型 = 保護者⇔教室でメッセージが往復し、教室からのお知らせが対象保護者にだけ見える状態。

### S. スケジュール

- 時間割・今後の予定ビュー（schedule_entries、種別凡例付き）。
- 欠席連絡 専用導線（保護者発信→教室受付。座席表・振替フローとの本連動は作り込み段階で）。
- **今月の残り振替回数の表示**（下記 §7-3）。
- v1 フォーム群の取り込み（擬似認証→本物アカウント、回答スコープ化）。
- 面談/体験セルフ予約（INQ予約系）のログイン文脈接続。
- 原型 = 紐付け生徒の予定が見え、欠席連絡が教室に届く状態。

### R. 報告書（最後の段）

- 保護者ビュー = P1-14 報告書×進行表マージの「ビュー2」。**P1-14 が未着手のため依存あり**。
- 公開承認ワークフロー: 講師下書き→室長承認→公開。承認前は保護者非表示。
- 原型 = 承認済み報告書が保護者に一覧・閲覧できる状態（マージ完成を待たず、既存報告書データの読み取りビューから始めることを許容する）。

### G. 成績（Stage 5・保護者の書き込み第一号）

- 保護者が **定期テスト・内申（通知表）を入力** → スタッフが承認 → 既存の成績（`assessments`）に転記。
- 保護者は自分の紐づけ生徒の**成績（スタッフ入力分も含む）を閲覧**できる。
- 模試の結果は対象外（成績表は塾に届く・CSVインポート運用済み。保護者に入れさせる意味がない）。
- 原型 = デモ保護者が定期テストを入力→スタッフが承認→`/students/[id]/scores` に反映され、保護者側でも承認済みとして見える状態。**詳細は §7-5**。

### 横断: 通知

- 最終形は確定済みの通知マトリクス（LINE push 一本。届ける=push／見れば済む=画面0円）。
- **クローズド期間は画面内新着表示のみ**（マイページのバッジ＋一覧の未読）。
- 実装は通知イベントを1箇所に集約し（notification dispatcher）、チャネル（画面内/LINE/メール）を差し替え可能にしておく。LINE 取得後に push チャネルを足すだけで済む構造にする。

## 5. 正典（account-line-design.md）からの変更点

基本は引き継ぎ。変えるのは以下だけ。

1. **実装着手を LINE 取得後としない → ID/PW 先行で今すぐ着手**
   - 正典は「実装はLINE取得後」としていたが、LINE取得（P1-0）は進捗ゼロのクリティカルパス。待つと土台開発が止まる。
   - portal_accounts は元々 login_id/password_hash を持つ設計なので、**ID/PW ログインだけで全機能が成立**する。LINE ログイン・LINE push は取得後に同じセッションへ着地させる（案3の利点）。
   - クローズド期間（アドミンのみ）は ID/PW で全機能検証できる。
2. **クローズド開発方式の追加**（§6。正典に無かった v2 固有の要件）
3. **通知はクローズド期間中、画面内のみ**（G7。正典の「LINEプッシュ一本」は最終形として維持）
4. **面談調整は当面お知らせ配信で代替**（G3。専用のセルフ予約接続は Stage 3）
5. **報告書の原型は P1-14 完成を待たない**（既存データの読み取りビュー先行を許容）

認証方式（案3: 自前ログイン→Supabase互換JWT→RLS）、データモデル（portal\_\*）、権限（invite_type）、失効（withdrawal_date 超過で自動失効）、チャット/掲示板のスキーマ案、通知マトリクス、コストモデルは**すべて正典のまま**。

## 6. クローズド開発方式（v2 固有）

### 6-1. ルート・コード分離

- 新領域は **`/mypage`**（ログイン制なので v1 と違い schoolCode 不要）。恒久名を最初から使い、公開時のリネーム churn を避ける。
- ログイン画面は `/mypage/login`、招待受諾は `/mypage/invite/[token]` を想定。
- 既存 `/portal/` 配下のファイルは変更しない。共有したいコンポーネントは移動せず import 参照のみ（v1 に影響を出さない）。

### 6-2. アクセス制御（クローズドの担保）

二段構え。

- **(a) 招待制**: portal_invitations の発行 UI・API を**アドミン限定**にする。招待が無ければ誰もアカウントを作れない＝構造的にクローズド。
- **(b) 全体スイッチ**: system_settings にポータル有効フラグ（例 `portal_v2_enabled`、既定 OFF）。OFF なら `/mypage` 全体を 404/準備中に。緊急遮断用。
- 公開段階での教室単位 ON/OFF は school_widget_settings 同型で後から足す（今は作らない）。

### 6-3. DB 分離度（不変条件）

- **追加するのは portal*\*・chat*\*・通知系の新テーブルのみ。既存テーブルのスキーマは原則変更しない。**
  - 例外は掲示板拡張（audience 列等）のみ。既定値=社内で既存動作を変えないこと。
- 既存テーブル（students / schedule_entries / 報告書等）へは**ポータル用 RLS ポリシーの追加**のみ（スタッフ用と併存）。既存ポリシーは触らない。
- **ポータルJWTは専用Postgresロール `portal` で発行する（2026-07-14 決定・本番PoC済み）**。
  - 理由: `authenticated` で発行すると「authenticated＝スタッフ」前提の既存の広いポリシー（subjects/curriculum_items/textbooks の全開放等）が保護者にも適用されてしまう。専用ロールなら**デフォルト全拒否**で、将来テーブルが増えても自動的に安全側。
  - 帰結: ポータルに見せるテーブルは今後も**明示的な `grant ... to portal` ＋ `to portal` ポリシー**が必要。忘れると見えないだけ（安全側に倒れる）。
  - 技術メモ: `auth` スキーマは portal に usage 付与不可（Supabase内部所有）のため、ポリシーでは `auth.uid()` でなく `public.portal_uid()`（request.jwt.claims から sub を読む自前関数）を使う。
- RLS 回帰テスト（既存 CI）にポータル用ポリシーのケース＋デフォルト拒否（portal で subjects 等が読めない）のケースを追加する。

### 6-4. 検証データ

- まず **is_test 生徒＋ダミーのポータルアカウント**で全機能を通す。
- 実在生徒データへの接続は読み取り系（スケジュール閲覧・報告書）から。書き込み系（チャット・欠席連絡）はアドミン自身のテスト運用で確認してから。
- 個人情報を新しい経路（ポータル JWT）に流す前に、RLS 境界テスト（自分の紐付け生徒のみ読める／他生徒は弾かれる／失効後は見えない）を必ず先に通す。

### 6-5. 本番デモ（教室長に触らせる・2026-07-15 確定）

本番環境に**ダミーデータだけのデモ**を置き、教室長（manager 以上）に体験させる。実データには一切つなげない。

**フラグ（6-2b）は ON にしない。** 理由:

- `portal_v2_enabled` は `system_settings` の**グローバルなキー1個**で、ON にすると `/mypage/login` が**本番に公開**される。「デモアカウントにだけ見せる」粒度が無い。
- さらにこのフラグは**レイアウトしか見ておらず、`/api/mypage/**`の16本は一切チェックしていない**。有効な`portal_session` cookie があれば API は応答する。つまりフラグは緊急遮断として機能しない（画面だけ消える）。

**代わりに「スタッフ認証を通したデモ専用セッション」で入る。**

- 入口: AppHeader の**設定（歯車）メニュー**内、「教室長ダッシュボード（試作）」の隣（`isManagerOrAbove`）。**navConfig には載せない**＝試作機能の入口をここ1箇所に集約する。
- **罠（実機で発覚）**: 素の `fetch` で `/api/portal-demo/start` を叩くと **401** になる。この API は `requireManager` を通るので、`Authorization` ヘッダーを明示的に付ける既存の **`fetchWithAuth`**（`src/lib/api/auth.ts`）を使うこと＝管理API呼び出しの作法。
- `POST /api/portal-demo/start` が `requireManager` でスタッフを検証 → デモアカウントの JWT を **`demo: true` クレーム付き**で署名 → `portal_session` cookie。
- `/mypage` レイアウトの門番を `フラグON || claims.demo` に変える。フラグは OFF のままなので**ログインフォームは本番に出ない**（未ログインの第三者は従来どおり 404）。
- `demo` クレームは署名鍵で守られており偽造できない。

**ダミーデータの隔離（三重）**:

1. **デモ教室** `schools.is_demo = true` — 教室ドロップダウン・cron 集計等から既存の仕組みで除外される。
2. **デモ生徒** `students.is_test = true` — 講習進捗・回答率等の業務集計から既存の仕組みで除外される。
3. **RLS** — `portal_students_select_linked` により、ポータルアカウントは**紐づけ生徒しか見られない**。デモアカウントをデモ生徒だけに紐づける限り、実データには**構造的に到達不可能**。

**安全弁**:

- `/api/portal-demo/start` は、デモアカウントの紐づけ生徒が**全員 is_test かつ is_demo 校**であることを毎回確認し、1人でも違えば発行を拒否する（データ側の事故が起きても構造的に塞ぐ最後の砦）。
- `notify.ts` の宛先解決が **is_test 生徒 / is_demo 校を宛先ゼロで返す**。ダミーデータから実在の保護者にメールが飛ぶ経路を、呼び出し側に依存せず1箇所で塞ぐ。
- デモアカウントの `password_hash` は**誰もログインできない値**にする。デモはスタッフ認証経由でのみ入る設計であり、将来フラグを ON にしたときに弱いパスワードの公開ログイン口が残らないようにする。

**スタッフ側（双方向の体験）**: 教室長以上を**デモ校の担当（user_schools）に加える**。受信箱 `/admin/portal-chat` は `auth.schoolIds` で絞るため、担当でないとデモ連絡が1件も見えず「保護者が送る→教室が返す」というポータルの核心を体験できない。

- **安全な理由**: 教室長以上11名のうち**8名は既に is_demo の「デフォルト教室」の担当に入っている**（2026-07-15 本番実測）ので、性質の変わらない追加。デモ生徒は `is_test` で業務集計から除外される。
- **使い方**: 教室切替で「デモ校（保護者ポータル体験）」を選ぶ（または「すべての教室」）。受信箱APIは school_id 未指定なら自分の全スコープを返す。
- **注意（UIに出る変更）**: `is_demo` の教室は**教室ドロップダウンに「デモ」バッジ付きで表示される**（`AppHeader.tsx` の `displaySchools = schools` にフィルタは無い。CLAUDE.md の「AppHeader が is_demo を除外する」という記述は古い）。よって担当に加えた教室長のドロップダウンに1項目増える。既に「デフォルト教室」が同様に出ているので性質は同じだが、**「既存UIは一切変わらない」とは言えない**点に注意。
- 対象は manager 以上のみ。講師（72名）には広げない。

**データ**: `supabase/demo/portal_v2_demo_data.sql`（冪等・固定UUID・日付は current_date からの相対）。

## 7-2. Stage 2 詳細仕様（2026-07-14 確定・UIモック承認済み）

UIモックで合意した設計。実装の契約。

### チャット（生徒ごと1スレッド・相手＝教室）

- テーブル: `chat_threads`(school_id/student_id/created_by/created_at, student_idにunique) / `chat_thread_participants`(thread_id/portal_account_id) / `chat_messages`(thread_id/**sender_kind: 'staff'|'portal'|'system'**/sender_id nullable/body/**template_kind** text nullable/**payload** jsonb nullable/created_at) / `chat_reads`(thread_id/reader_kind/reader_id/last_read_at)。

### テンプレ（構造化メッセージ）

- 種別 `template_kind`: `absence`(欠席・遅刻) / `transfer_request`(振替希望) / `meeting_request`(面談希望)。payload に日付・時限・理由・振替希望等を持つ。

- **振替ルール（2026-07-14 追加確定）**:
  - **締切: 対象授業の前日 21:00（JST）まで**。締切後〜当日は振替不可＝**欠席のみ**受け付ける。UIで振替希望を無効化（理由表示）し、**サーバー側でも必ず検証**（クライアント改ざん対策）。
  - **振替希望時は希望日時を第1〜第3希望まで入力**（第1必須、第2・第3も入力を促す）。payload に `candidates: [{date, slot}...]` として保持し、構造化カードに第1〜第3希望を表示。教室はその中から座席表で組む。
  - 受付の自動返信は締切判定を文面に反映（例: 締切内=「希望日時を確認し、振替日が決まり次第ご案内します」／当日=「当日のご連絡のため欠席として承りました（振替対象外）」）。

### 自動生成メッセージ（sender_kind='system'）★今回の追加要件

- **受付の自動返信**: 保護者が absence/transfer_request を送ると、**payloadの実日付を当てはめた受付メッセージをシステムが即時自動投稿**（室長は手打ち不要）。文面はサーバーで生成。
- **振替確定の座席表からの自動発信**: 座席表で振替コマを組んで確定した瞬間（`src/lib/api/schedule.ts` の `completeHeldTransfer`、既に `transfer_notifications` へpending行をINSERTしている箇所）をフックに、**実際の振替日・時限・科目を当てはめたシステムメッセージを保護者スレッドへ自動投稿**。

  - 冪等性: `transfer_notifications.id` または toEntry.id をキーに二重投稿を防ぐ。

### 掲示板 audience 拡張（唯一の既存テーブル変更）

- `bulletin_posts` に列追加: `audience text[]`（既定 `{社内}`）/ `target_scope text`（'all'|'grade'|'individual', 既定'all'）/ `target_grade int[]`（学年指定用）。個別指定は別テーブル `bulletin_post_targets`(post_id/student_id)。

## 7-3. 今月の残り振替回数（2026-07-14 追加確定・Stage 3）

保護者が「あと何回振替できるか」を自分で把握できるようにする。**ルールは既存の座席表と完全に同一**にし、判定ロジックを二重実装しない。

### 既存ルール（`src/lib/api/schedule.ts` の `getMonthlyTransferUsage` が唯一の正）

- **上限** = その生徒の有効な通塾日程パターン（`schedule_regular_patterns` の `is_active` 行数）。「週N回通う生徒は月N回まで振替できる」。
- **使用** = **振替元**（`schedule_entries.status='transferred_out'`）の `entry_date` がその月に含まれる件数。
  ★ 数える月は「**休んだ授業の月**」であって振替先の月ではない（月またぎの振替でも元の月に計上）。
- **残り** = `limit - used`（0未満は0表示）。
- スタッフ側は**ソフト上限**（超過してもダイアログ確認で例外登録できる）。

### ポータルでの扱い（確定・2026-07-14 モックレビューで改訂）

- **表示は控えめに**（振替は「権利」であって「推奨」ではない）。目立つカード表示はしない。
  予定ビューと欠席・振替シートに**小さな1行**（例: 「7月の振替 残り1回（2回まで）」）で示すのみ。
- **月の基準は「対象授業の日付の月」**（今日の月ではない）。8/1 に 7/31 の欠席を連絡したら 7 月分としてカウント・表示する（＝ `getMonthlyTransferUsage(studentId, 対象授業日)` を呼ぶ）。
- **上限到達時は原則ハードストップ**: 残り0なら「振替希望」を選べない（欠席・遅刻のみ）。
  文言例: 「今月の振替上限（N回）に達しています。振替をご希望の場合は教室にご相談ください」。
- **例外は教室の明示許可で解錠**: スタッフが生徒単位で「今月の振替を追加許可」した場合にのみ、
  保護者側に振替希望が再び選べるようになる（許可中である旨を表示）。
  実装: `portal_transfer_permissions`（school_id / student_id / month / extra_count or 無制限 / granted_by / created_at）を
  新設し、スタッフ受信箱 or 生徒詳細から付与・取消。上限判定は「limit ＋ 許可分」で評価。
- **振替無制限期間（講習前フリー期間）**: 教室が期間を設定でき、**対象授業日がその期間内なら上限判定をスキップ**する。
  実装: `transfer_free_periods`（school_id / start_date / end_date / label / created_by）。設定UIはスタッフ側
  （座席表設定 or /settings）。ポータル表示は「7/22〜8/9 は振替制限なし」の小さな注記。
- **残り回数は「確定済み」のみを数える**（保護者の未処理リクエストは `transferred_out` になっていないため未計上）。
  表示にはその旨が伝わる文言を使う。
- **実装**: `getMonthlyTransferUsage` を再利用する。ポータルからは service role のサーバー API
  （`/api/mypage/transfer-usage?studentId=`）経由で取得し、**必ず「そのアカウントの紐づけ生徒か」を検証**する
  （`schedule_regular_patterns` を portal ロールに grant しない＝ポータルに素の座席表テーブルを開けない）。
  許可・無制限期間の判定もこのAPIに集約し、クライアントは結果（残り数/許可中/無制限期間中/停止中）だけ受け取る。
  **サーバー側のテンプレ投稿APIでも同じ判定を再検証**する（締切ルールと同じ二重チェック方針）。
- **表示は在籍中の紐づけ生徒のみ**（Stage 1 の students ポリシーと同じ失効挙動に従う）。

### 申し込みプッシュ（手続きハブの「あなた宛のご案内」・2026-07-14 追加確定）

- 「受付中」の羅列だけでなく、**その生徒が申し込むべきフォームを個別に知らせる**。
- ハブ上部に「〇〇さんへのご案内」セクションを設け、該当フォームを強調カード＋理由付きで表示
  （例: 「7/10 に教室からテスト対策のご提案があります → お申し込みください」）。
- 対象の導出（初期スコープ）:
  1. **テスト対策 増コマ**: その生徒宛の提案書（test_prep_proposals）が **sent/公開済み** で、対応する増コマ申込が未提出のとき。
  2. **模試（moshi/mogi）**: 開催中の form_period の対象学年に生徒が含まれ、未申込のとき（教室単位の推奨フラグは将来）。
- プッシュ表示と同時に通知（画面内＋メール）1回。しつこくしない（未申込でも再通知はしない。実装はディスパッチャ経由）。

## 7-5. Stage 5 詳細仕様: 成績の保護者入力＋閲覧（2026-07-16 設計）

### 設計の3本柱

1. **入力対象は 定期テスト（regular_test）と 内申（report_card）だけ**。
   保護者の手元に原本がある（テスト用紙・通知表）＝保護者が一次情報源。塾側の聞き取り・回収の手間をゼロにする。
   模試（mock）は成績表が塾に届き CSV/貼り付けインポート運用が既にあるため**入力対象にしない**（閲覧はできる）。
2. **保護者の入力はそのまま業務データに混ぜない**。中間テーブル `portal_score_submissions` に置き、
   **スタッフの承認で `assessments` / `assessment_scores` へ転記**する。
   → AlertBoard・成績グラフ・PDF・生徒詳細など既存の全消費者は**無改修のまま「承認済みだけ」を見続ける**。
   報告書の「承認＝公開」ゲート（§7-4）の**逆向きの適用**（保護者→塾は「承認＝取り込み」）。
3. **portal ロールに書き込み権限を一切足さない**（§6-3 の不変条件）。
   書き込み = service role API ＋ 入口で `requirePortalStudent`（チャット投稿と同じ型）。
   読み取り = SELECT のみ（自分の申請は RLS、承認済み成績は狭いビュー）。

### データモデル（新規1テーブル＋ビュー1本。既存テーブルのスキーマ変更なし）

```
portal_score_submissions
  id            uuid PK
  school_id     uuid NOT NULL → schools      -- 生徒の所属校を送信時に焼き込み（承認キューの教室絞り。
                                             --  student_textbooks.school_id と同じ「所属校と一致」原則）
  student_id    uuid NOT NULL → students
  account_id    uuid NOT NULL → portal_accounts   -- 誰が入れたか
  category      text CHECK ('regular_test','report_card')   -- ★模試はDB層でも入れられない
  grade         int  CHECK (1..13)
  name_code     text                          -- assessments.name_code と同じ値域（term1_mid 等）・同じCHECK
  exam_month    date                          -- 月初日正規化（portal_transfer_permissions.month と同じ流儀）。
                                             --  report_card は null 可（assessments 側の運用と同じ）
  scores        jsonb NOT NULL                -- {"english": 82, ...}。表示前に防御的正規化
                                             --  （homework_assignments / subject_specific と同じ思想）
  status        text CHECK ('submitted','approved','rejected') default 'submitted'
  rejected_reason text                        -- 差し戻し理由。★保護者に見せる（報告書の rejection_reason は
                                             --  内部向けで見せないが、こちらは保護者への返答そのもの）
  reviewed_by   uuid → user_profiles
  reviewed_at   timestamptz
  assessment_id uuid → assessments            -- 承認で転記した先（監査・二重転記防止）
  created_at / updated_at
```

- **GRANT**: service_role=ALL ／ portal=SELECT（`account_id = portal_uid()` の自分の申請のみ・policy）／
  authenticated=SELECT（`check_school_access(school_id)`。承認キューの表示用。**承認操作そのものはAPI経由**）
- **値のバリデーション（サーバー・service role APIの入口）**: 定期テスト=整数0〜100 ／ 内申=整数1〜5 ／
  科目キーはカテゴリの既知集合（`COMMON_9_SUBJECTS`）のみ通す。範囲外・未知キーは400。
- **閲覧ビュー `portal_assessments`**（§7-4 の限定公開ビューと同型・security_invoker 無し）:
  - 述語: 紐づけ（`portal_uid()`）＋在籍中＋生徒の所属校＝assessments.school_id（4条件は §7-4 と同じ）
  - 列: id / student_id / category / grade / name_code / exam_month / exam_date / scores（jsonb集約）。内部列なし
  - **スタッフが入れた成績（模試含む全カテゴリ）も保護者に見せる**（設計判断: Grow置換として自然。
    絞りたくなったら述語に category 条件を足すだけの構造にしておく）
  - relation（保護者/生徒本人）では絞らない＝本人にも自分の成績は見せる

### フロー

1. **保護者**: `/mypage/grades` — 承認済み成績の一覧＋自分の申請と状態（承認待ち/承認済み/差し戻し＋理由）。
   「成績を入力」→ カテゴリ・テスト名（`ASSESSMENT_NAME_OPTIONS` の選択式）・学年・年月（ピッカー）・
   科目別点数（数値のみ）→ `POST /api/mypage/scores`。
   **保護者にもタイピング最小化を適用**: 自由入力は一切なし（選択＋数値だけ）。
   - 再送: 同一（student, category, grade, name_code, exam_month）で自分の `submitted` が既にあれば**置き換え**。
     承認後の訂正は新しい申請として出す（承認済みの行は保護者から不変）。
2. **スタッフ**: 承認キュー（生徒管理ページの NewResponsesBoard と同型の「承認待ち成績」ボード＋
   `/students/[id]/scores` 内のバナー）。既存 `assessments` に同一（category, grade, name_code, exam_month）の
   行があれば**並べて差分表示**。
   - **承認** = 転記。無ければ `createAssessmentRow` 相当＋scores 埋め、あれば**申請に含まれる科目だけ上書き**
     （空欄・未申請の科目は触らない）。`reviewed_by` / `assessment_id` をアトミックに記録。
   - **差し戻し** = 理由必須（保護者に表示される）。
   - 権限境界は既存の成績編集と同じ **`canEditScores`（講師も可）**。承認＝成績を書く行為なので同じ境界に置く。
3. **通知**: クローズド期間は画面内のみ（保護者=状態表示／スタッフ=キューのバッジ）。
   メールは既存の宛先解決課題（§8）に相乗りしない。

### デモ・検証

- デモ校に「承認待ち1件＋差し戻し1件＋承認済み数件」を仕込む（demo SQL に増分。冪等原則は維持）。
- RLS境界テスト: portal が portal_score_submissions の他人の行・assessments 本体・ビュー越境を読めないこと／
  書きAPIが他人の生徒・退塾生・模試カテゴリ・範囲外の値を弾くこと。
- 出口条件: デモ保護者が定期テストを入力→スタッフが承認→`/students/[id]/scores` に出る→保護者の
  `/mypage/grades` にも承認済みとして出る（一周）。
