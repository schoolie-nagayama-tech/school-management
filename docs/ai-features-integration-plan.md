## 0. これは何か

2026-09-02〜09-03 に一つずつ決めてきたAI機能を、**どの既存画面のどこに置くか**に落とす。
新しい画面は作らない。**すべて既存の画面の中に入る。**

あわせて、別で設計していた **連絡掲示板AIアシスト**（講師が連絡事項に取り組んだかをAIが見る仕組み。
正典 [docs/bulletin-ai-assist.html](./bulletin-ai-assist.html)）と、
**⑬報告書のガイド**（[docs/lesson-report-flow-plan.md](./lesson-report-flow-plan.md)）を
同じ枠に入れる。この2つは他のAI機能と**同じ画面を取り合う**ので、別々に決めると衝突する。

## 2. 画面ごとの変更

実装は画面単位で進む。機能単位ではなく**画面単位**にまとめ直したものが以下。

### 2-1. 報告書フォーム `/lesson-reports/[scheduleEntryId]`

**3つのAI機能が同じ画面に乗る。**ここが最も混み合う。

| 何を | どこに |
| --- | --- |
| ガイド（⑬） | 上部の sticky バー＋フローティングカード。**既存の `ReportGuideBar` を作り替える** |
| 講評を整える | 講評欄（ガイドのステップ `review`）の下にボタン1つ |
| 授業中ポップアップ | 画面の隅。**「授業を記録」を押した時点で起動**し、経過1/3・2/3で1件だけ出す |

**衝突する点（ここを決めておかないと事故る）:**

- ガイドは講師の注意を1問ずつに集める作りで、**ポップアップはその邪魔をする**。
  → ポップアップは**ガイドの質問に答えている最中は出さない**。
  カードを閉じている時・フォーム表示に切り替えている時だけ出す。
- 「整える」はガイドのステップ `review` の中にあるので、
  **整えた結果がステップの完了判定を壊さない**こと（文字数が変わるだけで完了は維持）。

**⑬で今回決めたこと（実装との差分は §4）。**

### 2-2. 掲示板の投稿モーダル `BulletinPostModal`

**1つのモーダルに、配信先で切り替わる2つのAIが入る。**
モーダルには既に `deliversToPortal`（audience に保護者/生徒を含むか）という判定がある。
**これをそのままAIの出し分けに使う。**

| 配信先 | AIの仕事 | 出力 |
| --- | --- | --- |
| 社内のみ | **整えるだけ。**箇条書きを箇条書きのまま | 行を増やさない・減らさない・順番を変えない |
| 保護者を含む | **お知らせの体裁に流し込む** | `{title, lead, items[], note, closing}` |

宛先「保護者の皆さまへ」と日付は**システムが入れる**。AIは書かない。

さらに**投稿した後**に、その投稿から**13種の有限カタログ**でタスクを抽出する（§3）。

### 2-3. 教室長ダッシュボード `/dashboard`

最上部の「今日やること」。**2段構え。**

- **1段目**: 毎朝10:00に自動生成。既存のGoogleカレンダー連携（`google_calendar_tokens`・4アカウント）を流用。
- **2段目**: あとから出てきた用事をどこに挟むかだけAIが決める。返すのは `{block, when, why}` のみ。

★**全体を作り直させない。**作り直すと、消した項目とドラッグで並べ替えた順序が壊れる。

★**勤務の時間がまだ材料に入っていない**（[today-plan-ai-plan.md](./today-plan-ai-plan.md) §6）。

### 2-4. 保護者チャット `/admin/portal-chat`

教室長が箇条書きを書き、**AIがスレッド全体を読んで**流れに合う文章にする。

- **宛名を書かない**（チャットなので）。
- 返信のときは**何に返信しているかを引用で見せる**。
- スレッドが空なら「教室から始める連絡」として、返事をする書き方にしない。

★**振替は座席表から連絡、欠席は定型句**で足りる。実データ95件の返信の中央値は84字で、
AIが要るのは**3〜4スレッド（約3%）**だけ。ここは期待値を低く持つ。

### 2-5. 提案書エディタ `ProposalEditor`

科目ごとにコンセプトを作り、**載せるかどうかは教室長が決める**。

★**保存先の列が無い。**`theme` は一言ラベル、`notes` は「印刷には出ません」と明記された内部メモ、
`seasonal_proposal_units.reason` は入力UIが無く常に空で保存される死んだ列。
→ **`seasonal_proposals` に列を1つ足すところから。**

### 2-6. 面談ワークスペース `/interview`

左カラム「前回の申し送り」の下に**報告事項カード**。固定7セクション、各2行。
**現状の行はシステムが組み、AIは「見えること」だけ**書く。

材料はこの画面がほとんど読み済み。足りないのは**出欠**（生徒の出欠集計関数が無い）と
**保護者とのやりとり**（`chat_threads`）の2つ。

### 2-7. 進行表 `LastHandoverCard`

引継ぎを**時系列のまま畳む**。1回=1行。まとめて1文にすると「いつからそうなったか」が消える。
経緯・ずっとある課題・できること/できないこと・次に気をつけること・**懸念点**を分けて出す。

## 3. 連絡事項の監視（掲示板AIアシスト）は2画面にまたがる

11機能のうち、**これだけが1画面で完結しない。**

```
掲示板の投稿（室長）
  → ① 投稿を読んで13種のカタログからタスクを選ぶ（自由生成しない）
  → ② 済/未済は実データで判定する（手動チェックは二重帳簿なので見ない）
  → ③ 報告書フォームで「授業を記録」を押した講師に、授業中に1件だけ出す
```

**②が要点。** 清瀬校の実例では、室長は手動の帳簿を見て「59名中14名」と督促を4回繰り返していたが、
**同時点で実データ（`assessments`）には41名が入力済み**だった。実態はチェックの付け忘れで、
督促そのものが不要だった。**だから済判定は実データ側で行う。**

**既定は出さない側**（誤爆より見逃しを選ぶ）。期限当日・超過だけプログラムで強制的に出す。
未対応0件ならAIを呼ばない（コストゼロ）。

**実装前に決めることが4つ残っている**（[bulletin-ai-assist.html](./bulletin-ai-assist.html) §10）。
いちばん大きいのは **手動チェック運用を続けるかやめるか**で、これで機能の性格が変わる。

## 4. ⑬報告書ガイドの、実装との差分

ガイドバーは **PR #102 で実装済み**（`src/lib/lesson-reports/guideSteps.ts`・10問）。
今回のモックで決めたことを反映すると **14問**になり、順番も変わる。

**新しい順番:**

1. 今日の様子 → 2. ゴールの達成 → 3. **学校進度** → 4. ゴール → 5. **指導範囲（開始）**
→ 6. 宿題の確認 → 7. 確認テスト → 8. 次回の宿題 → 9. 科目 → 10. **講評**
→ 11. **指導範囲（終了）** → 12. **今日の演習の正答率** → 13. 次回の予定 → 14. 引継ぎ

**変更点:**

| # | 変更 | 理由 |
| --- | --- | --- |
| 1 | **指導範囲を開始/終了に分ける** | 「どこから」は授業開始時に聞けるが「どこまで」は講評の後にしか分からない |
| 2 | 今日の演習の正答率も講評の後へ | 同上 |
| 3 | 学校進度を3番目に | 授業前に分かっていることを先に片づける |
| 4 | 次回の予定を引継ぎの隣に | 次回の話は続けて聞く |
| 5 | 次回の予定に「表から選ぶ」を追加 | 進行表からの自動に加えて手で選べる |
| 6 | **宿題をテキスト名とページに分ける**＋テキスト名の自動補完 | タイピングを減らす |
| 7 | 進捗の丸をクリックでその質問に戻れる | 戻る導線が無かった |
| 8 | 最後の「書いてないところ」から該当質問へ飛べる | 指摘だけでナビが無かった |
| 9 | フローティングカードから提出できる | 最後まで書いたらそのまま出せる |

★**表示側のフィールドは1つのまま。** 開始と終了で聞くが、書き込む欄は同じ。

★**保存経路は増やさない。**ガイドはプレゼンテーション層だけ（既存の大原則）。

## 5. 共通土台（1度だけ作る）

- `/api/ai/**` の Route Handler。**サーバー側のみ**・鍵はVercel環境変数・教室スコープ検証。
- **渡すフィールドのホワイトリスト列挙**（`select('*')` を流さない）。
  住所・電話・メール・LINE ID・支払い情報は送らない。
- 主力 Haiku、難所だけ Sonnet。
- 「判断しない」ときに黙る設計を全機能で揃える（掲示板アシストの「既定は出さない」と同じ原則）。
- ★**`docs/legal/privacy-policy.md` 第5条の委託先一覧に Anthropic を追記。**
  公開前に必須で、機能ごとではなく1回で済ませる。

## 6. 採らないもの: 追客メール（2026-09-03 判断）

実データを見て**却下**した。理由:

- テンプレートは**すでに8本あり完成している**（1/4/10/20/30日後＋手動3本）。文面は問題ではない。
- これまでに送った追客メールは **24通**。うち23通が機能公開月に集中し、それ以降は1通。
- メールが届いた **20件は全員が連絡不通・没・体験没**。入会した人はゼロ。
  諦める直前の最後の1通として使われている。
- 落としているのは **資料請求**（113件・入会14.2%・連絡不通54.0%）。
  そのうち **86件は接触記録がゼロ**。体験（47.5%）・学習相談（70.6%）は電話で成立している。

→ **AIが書く話ではなく、テンプレートの出し分けと送信導線の問題。**
やるとすればテンプレートの変更なので、AI機能としては扱わない。
