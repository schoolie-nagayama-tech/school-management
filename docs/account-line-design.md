## 1. 基本方針

- **自前アカウントを軸（主）、LINEを連携・通知チャネル（従）** とする。
- 保護者の住所・電話などPIIは**別システムが正**。本アプリの保護者レコードはPIIをほぼ持たない。
- スタッフ（教室長・講師）の認証は**従来のメール/パスワード（Supabase Auth）のまま**。
  保護者・生徒の認証とは主体で分離する。

---

## 2. 用語

| 用語               | 意味                                                                          |
| ------------------ | ----------------------------------------------------------------------------- |
| ポータルアカウント | LINEログイン等で認証する**保護者・生徒本人**のアカウント（`portal_accounts`） |
| スタッフアカウント | admin/owner/manager/teacher（既存 `user_profiles`・Supabase Auth）            |
| 紐づけ             | ポータルアカウントと生徒の関係（`portal_account_students`）                   |
| 招待               | 教室が発行し、保護者/生徒が紐づけに使うトークン（`portal_invitations`）       |

## 3. データモデル

生徒テーブル（`students`）は**無変更**。外側に薄い保護者・生徒レイヤーを足す。

```
students(登録済・無変更) ──< portal_account_students >── portal_accounts
                                                              ▲
                                          portal_invitations ─┘（招待で紐づけ）
```

### portal_accounts（保護者・生徒を統合・PIIなし）

```
id              uuid PK
line_user_id    text unique nullable   -- LINE連携した人だけ
login_id        text unique nullable   -- フォールバック用（教室発行）
password_hash   text        nullable   -- フォールバック用
display_name    text                   -- LINEプロフィール名 or 教室入力
avatar_url      text        nullable
last_login_at   timestamptz
created_at      timestamptz
-- email / phone / 住所 は持たない（別システムが正）
-- line_user_id と login_id は「どちらか一方でも両方でも」可
```

### portal_account_students（多対多の紐づけ）

```
account_id  uuid -> portal_accounts.id
student_id  uuid -> students.id
relation    text  -- 'self' | 'guardian' | 'other'（+ relation_note: otherの自由入力）
PRIMARY KEY (account_id, student_id)
```

- 生徒本人: `relation='self'` で自分の生徒IDに1本
- 保護者: 子（兄弟は複数行）に `guardian`（既定）または `other`（続柄を自由入力）で紐づく
- 父・母それぞれが別 `portal_accounts` で同じ生徒に紐づける

### portal_invitations（招待。既存 user_invitations の発想を流用）

```
token          text
student_id     uuid -> students.id
invite_type    text  -- 'guardian' | 'student'  ※relation と閲覧権限を確定
expires_at     timestamptz
accepted_at    timestamptz nullable
accepted_by    uuid nullable -> portal_accounts.id
created_by     uuid -> user_profiles.id（発行スタッフ）
```

- 招待タイプを**教室が発行時に指定** → 生徒が「保護者」を自称して請求を覗く等の自己昇格を防止。

## 4. 認証・セッション（案3: 自前ログイン → Supabase互換JWT → RLS）

### 方式

```
LINEログイン or フォールバックID/PW を「自前で」検証
        ↓
Supabase互換のJWT（sub = portal_account_id）を署名して発行
        ↓
そのJWTでアクセス → RLS が auth.uid() を読んで DBレベルで認可
```

- `auth.users` に擬似ユーザーを作らない（パスワードハック不要）。
- **認可はRLSポリシーに集約**（多層防御）。`/api/portal/*` のチェック書き忘れによる漏洩を防ぐ。
- ログイン手段は自前なので **LINE / ID・PW の複数方式が同じセッションに着地**できる。

### なぜ案3か（検討経緯）

| 案                         | 認可の置き場所          | リスク                                                                      |
| -------------------------- | ----------------------- | --------------------------------------------------------------------------- |
| 案2 service-role＋アプリ層 | 各APIに散在             | エンドポイントでチェック書き忘れ → 漏洩。整合性が崩れやすい                 |
| 素の案1 Supabase Auth      | RLS（DB集約・多層防御） | LINE非対応のため擬似ユーザー+パスワードのブリッジ自体がバグ・セキュリティ源 |
| **案3（採用）**            | **RLS（DB集約）**       | 自前ログイン + 自前署名JWT で案1のハックを回避しつつRLSを得る               |

- 実装時の検証事項: 「自前JWTをSupabaseのJWTシークレットで署名 / Third-Party Auth登録 → RLSが auth.uid() を受理」を最終確認する。
  - **✅ 2026-07-14 検証済み**（`experiments/portal-auth-poc/`）: 本番プロジェクトは非対称署名鍵（JWT Signing Keys）方式のため、HS256共有シークレットでの自前署名は不受理（`PGRST301`）。
    代わりに **自前生成したES256鍵をSupabaseにインポート→Rotateで有効化→その鍵で自前ミント**する方式（Supabase公式FAQ記載の手順）で成立を確認した。
    `auth.uid()` が JWT の `sub` を正しく返すことを実機テスト済み。実装時はこの鍵を安全な環境変数（Vercel env、`NEXT_PUBLIC_`禁止）で管理する。
  - **✅ 同日追記: ロールは `authenticated` でなく専用の `portal` ロールを使う**。authenticated で発行すると「authenticated＝スタッフ」前提の既存の広いRLSポリシー（subjects 等の全開放）が保護者にも適用されるため。
    `create role portal nologin noinherit` ＋ `grant portal to authenticator` で PostgREST が成り代われることを本番で実測（pg_role=portal / subjects は403=デフォルト拒否）。
    `auth` スキーマは portal に usage 付与不可のため、ポータル用ポリシーは `auth.uid()` でなく `public.portal_uid()` を使う。
- RLSコスト: ポータルが読むテーブル（students / schedule_entries / 報告書等）に、**スタッフ用ポリシーと併存する形でポータル用ポリシー**を追加する必要がある。

### 認証手段の使い分け

| 主体     | 主たる認証                | フォールバック                                          |
| -------- | ------------------------- | ------------------------------------------------------- |
| 保護者   | LINEログイン              | 基本不要（希望時のみ教室発行ID/PW）                     |
| 生徒本人 | LINEログイン（あれば）    | **教室発行ID＋PW**（LINE無い子・共有タブレット/PC対応） |
| スタッフ | メール/パスワード（従来） | —                                                       |

- LINE LoginはWeb OAuthなので**タブレット/PCのブラウザでもログイン可**（LINEアカウントは必要）。
- LINEアカウントを持たない生徒（小中学生に多い）のため、生徒には**デバイス非依存のID/PWフォールバック**を用意。現状の擬似認証(`student_code`)を本物のログインに格上げした位置づけ。

## 5. オンボーディング（実務フロー）

### 事前（教室・一度きり）

1. LINE公式アカウント開設。
2. LINE Developers でプロバイダー作成 →（同一プロバイダー内に）**Messaging APIチャネル**＋**LINE Loginチャネル**作成。
3. アプリに各チャネルの認証情報を環境変数登録。

### 保護者/生徒ごと

```
教室                              保護者/生徒
─────────────────────────────────────────────────
1. 生徒を選び招待を発行
   （invite_type=guardian/student を指定）
   → コード/QR/URL 生成
                                  2. 公式アカウントを友だち追加
                                  3. LIFF/Webで「LINEでログイン」
                                     → line_user_id 取得
                                     → portal_accounts 自動作成
                                  4. 招待コード入力（QRなら自動）
                                     → portal_account_students に紐づけ
─────────────────────────────────────────────────
✅ identity確定 ＋ 生徒紐づけ ＋ 友だち追加 が一度に完了
```

- 兄弟: 同じアカウントが2人目の招待コードを入力 → 紐づけをもう1行追加。
- LINE無し生徒: 教室が ID/PW を発行 → 任意デバイスのブラウザでログイン → 招待で紐づけ。
- 自動一括紐づけは不可（世帯キーがデータに無い）。招待ごとに順次紐づける運用。

## 6. コストモデル（LINE Messaging API）

課金は **送信人数 × 配信回数**（プッシュ1配信を300人に送れば300通）。

- 応答メッセージ（保護者の発話への返信）は**無料・カウント外**。
- 保護者が見に来る画面（LIFF/Webダッシュボード・掲示板）は**通数ゼロ**。

| プラン                       | 月額    | 無料通数/月 | 超過       |
| ---------------------------- | ------- | ----------- | ---------- |
| コミュニケーション（フリー） | ¥0      | 200通       | 送信不可   |
| ライト                       | ¥5,000  | 5,000通     | 送信不可   |
| スタンダード                 | ¥15,000 | 30,000通    | 従量課金可 |

※2026年10月に追加メッセージ料金が「20万通境の2段階」へ改定予定（塾規模では当面無関係）。

### 自塾の前提（生徒約300人・公式アカウント1本）

- 一斉連絡 週2回のみプッシュ: `300×2×4.3 ≈ 月2,580通` → **ライト¥5,000 で収まる**。
- 一斉＋個別通知も全部プッシュ: 5,000通超 → **スタンダード¥15,000**。
- **設計レバー**: 「届けたい連絡＝プッシュ」「見れば済む情報（報告書・出欠・ダッシュボード）＝LIFF閲覧(0円)」と切り分けると年¥6万で回る。全プッシュは年¥18万。線引きが年¥12万差。

- LINE公式アカウント料金: https://www.lycbiz.com/jp/service/line-official-account/plan/
- Messaging API料金: https://developers.line.biz/ja/docs/messaging-api/pricing/

### 6.1 通知マトリクス（確定）

通知手段は **LINEプッシュ一本**（無料Webプッシュ基盤は既存だが、ポータルでは使わずスタッフ用のまま）。
方針: 高頻度・全員 → 画面で閲覧(0円)／緊急・重要・低頻度 → LINEプッシュ。

| イベント                         | 手段                   | 備考                                                         |
| -------------------------------- | ---------------------- | ------------------------------------------------------------ |
| 授業報告書 公開                  | **LINEプッシュ**       | 毎回だと通数大。「週1まとめ」で圧縮する選択肢あり（6.2参照） |
| 欠席・遅刻 記録                  | **将来LINE**           | ①出欠自動登録の完成後に有効化。当面は画面                    |
| 予定変更（振替・休講・コマ変更） | LINEプッシュ           | 行動が変わる重要通知                                         |
| 宿題 登録/更新                   | 画面のみ               | **報告書の記述から拾って表示**（専用データは作らない）       |
| 1対1チャット 新着                | LINEプッシュ           | 「新着あり」を1通に集約                                      |
| 掲示板 一斉連絡                  | LINEプッシュ           | 週2回想定の主役                                              |
| 掲示板 個別/学年宛               | 内容で判断             | 重要=LINE／通常=画面                                         |
| 入退室（①将来）                  | 画面（希望者のみLINE） | 毎回プッシュは通数最大                                       |

## 9. マイページ・④・⑤の決定（方針確定／詳細はこれから）

### マイページ（ダッシュボード）掲載項目（確定）

- 時間割・今後の予定 / 出欠サマリ / 授業報告書 / 宿題（報告書から拾って表示）
- **請求はここでは管理しない**（別管理）。生徒(self)には保護者向け情報を出さない。

### ④ 1対1コミュニケーション（確定）

- **アプリ内チャット**（チャットUI）。履歴はアプリに残る。新着は「新着あり」をLINEプッシュで1通集約。
- 相手は **教室（室長）宛の1本**（講師個別宛にはしない）。
- スレッドは **生徒ごと** に作成。参加者（保護者/生徒）は **室長が指定**。
- 保護者/生徒側から開始した場合は **1対1**（その人 ↔ 教室）で会話。
- スキーマ案:
  - `chat_threads`: id / school_id / student_id / created_by(staff) / created_at
  - `chat_thread_participants`: thread_id / portal_account_id（室長が指定。相手発信の1対1は1名）
  - `chat_messages`: id / thread_id / sender_kind('staff'|'portal') / sender_id / body / created_at
  - 既読: `chat_reads`（thread_id / reader_id / last_read_at）で管理

### ⑤ 掲示板（確定）

- **既存 BulletinBoard を拡張**（保護者・生徒用に新規作成はしない）。
- audience を付与: **社内 / 保護者 / 生徒**（複数可）。既定は社内（社内連絡と保護者連絡を混在させない）。
- 配信単位: **全体 ＋ 学年 ＋ 個別生徒** の3粒度。
- 既読: 現 `bulletin_reads.user_id`（スタッフ前提）に加え、portal_accounts 向け既読を別管理
  （例: `bulletin_reads` に reader_kind を追加 or 専用テーブル）。

### 招待運用（確定）

- 配布方法: **紙のQR/URLを印刷**（面談・送付で手渡し）＋ **メール送信**（保護者メールがあれば。ポータルの `form_responses.email` を流用可）。
- 有効期限: **7日**（既存 `user_invitations` の流用）。失効したら再発行。

### アカウント失効（確定）

- **`students.withdrawal_date` を超えたら、その生徒への紐づけを自動失効**（RLSポリシーで閲覧不可に）。
- 兄弟が在籍中なら保護者アカウント自体は有効（失効するのは当該生徒の紐づけのみ）。
- 卒業・退塾後のマイページ閲覧は **即時に不可**（猶予期間は設けない）。
