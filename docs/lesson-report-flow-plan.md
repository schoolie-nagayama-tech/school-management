# 報告書のフロー化（ガイドバー）設計書

作成: 2026-08-31 ／ 状態: **確定（実装中）**
対象: `/lesson-reports/[scheduleEntryId]`（報告書×進行表 統合フォーム、PR #64）

> **2026-08-31 ユーザー判断で方式確定**: ウィザード型（1問1画面で他が見えない）ではなく
> **「ゆるいガイド」**。項目ごとに質問に答えていったら書き終わっていた、くらいの体験。
> いつでも離脱して別の場所を直接書ける。ステップ構成（11問・時系列）はそのまま承認。

## 1. 目的

- **講師のわかりやすさ**: 統合フォームは1画面に情報が多く、新人講師は「どこから書けばいいか」で迷う。
- **漏れなく一定のクオリティ**: 提出前チェック（指導範囲・引継ぎ・講評）はあるが、書き終わってから不足を指摘される体験になっている。書いている途中で順に埋まる形にする。
- **オンボーディングとして機能**: 質問に答えて進めば報告書が完成する。教わらなくても書ける。
- 確立できたら他の機能（面談記録など）にも流用する。

## 2. 大原則: 保存経路・状態を増やさない

ガイドモードは**プレゼンテーション層だけ**を変える。

- フォーム state・自動保存（G）・提出前チェック（F）・進行表転記・保護者プレビュー（E）は**既存のものをそのまま使う**。ガイドは「同じ state を、別の順番・別の見せ方で編集する」だけ。
- したがって**途中でフォーム表示に切り替えても入力は1文字も失われない**。逆も同じ。
- 保存経路の二重化はこのプロジェクトで繰り返し事故になってきたパターンなので、ガイド専用の保存処理は一切作らない。

## 3. 方式: ガイドバー（モード分割はしない）

別画面のウィザードは作らない。**フォームの上に sticky の「ガイドバー」を貼る**だけにする。

- バーには「Q4/10 確認テストはやった？」のように**いまの質問**と進捗を出す。
- 「ここに答える」→ 該当セクションへスクロールし、数秒ハイライト。入力はフォーム本体で行う
  （入力UIを二重に作らない）。
- 質問に答える（state で自動判定）か「済にする／今回はなし」を押すと、**次の未完了の質問へ**進む。
- **拘束しない**: フォームのどこを直接編集してもよい。バーは常に「次の未完了」を指すだけ。
  順番どおりに書かない講師の邪魔をしない。
- バーは「×」で閉じられる（localStorage `lesson_report_guide` で記憶。既定=表示）。
  全問済みになるとバーは「あとは提出だけ」になり提出ボタンへ誘導する。
- 下書き自動保存・提出前チェック・保護者プレビューは従来のまま。

### 完了判定（ステップごと）

state から自動で判定できるものは自動、できないもの（「該当なし」が正解になりうる質問）は
バー上の「済にする」タップで進める。手動の済はページ内 state のみ（保存しない。
再訪時に自動判定分だけ復元されれば十分で、済フラグの永続化はデータを増やすだけ）。

## 4. ステップ構成

> **★この節の11問は 2026-09-03 の改訂（§9）で 14問に置き換わった。**
> 考え方（時系列・1画面1トピック・タップ中心）はそのまま。順番と分割だけが変わる。

授業を思い出す時系列に沿って聞く。1画面1トピック、入力はタップ中心（講師UIはタイピング最小化）、
手書きが要るのは「引継ぎ」「講評」の2つだけ＝既存方針のまま。

| #   | 質問（画面上部に大きく出す）   | 入力UI                                         | スキップ条件                      |
| --- | ------------------------------ | ---------------------------------------------- | --------------------------------- |
| 1   | 今日の様子で当てはまるものは？ | 遅刻・宿題未実施のトグルピル（既存）           | なし（該当なしで次へ）            |
| 2   | 今日はどこをやった？           | 進行表グリッド（既存・単元タップ）             | 教材なし生徒→自由記述欄に差し替え |
| 3   | 宿題・演習のでき具合は？       | 達成度スライダー（既存）                       | 宿題行が無ければスキップ          |
| 4   | 確認テストはやった？           | やった→点数入力（合否は自動判定） / やってない | なし                              |
| 5   | 学校はいまどこ？               | 学校進度列（既存・聞けたときだけ）             | 任意（あとででもOKを明示）        |
| 6   | この授業のゴールは何だった？   | 今日の目標（1文・手入力）                      | なし                              |
| 7   | 次回は何をやる？               | 次回の予定（自動提案を確認→違えばピッカー）    | 自動提案そのままなら1タップ       |
| 8   | 次回までの宿題は？             | 日割り行（既存・自動生成済みを埋める）         | なし                              |
| 9   | 次の先生への引継ぎ             | 手書き（内部のみ・保護者に出ない旨を明示）     | なし（必須）                      |
| 10  | 保護者へのメッセージ           | 講評（手書き）。**⑭のAIフック位置**            | なし（必須）                      |
| 11  | この内容で保護者に見えます     | 保護者プレビュー（既存 ReportDetail）→ 提出    | —                                 |

- ステップ6（目標）を内容（2〜5）の**後**に置くのは意図的。文書の表示順は「目標→内容」だが、
  授業後に思い出す順は「やったこと→ゴールは何だったか」の方が書きやすい。表示順は保存側で従来どおり。
- 進捗バー（「10問中4問目」）＋「あとで書く」で先送りしたステップは最後にまとめて再提示。
- 各ステップの完了判定は**既存の validateForSubmit の判定をステップ単位に割り当てる**
  （指導範囲=Step2 / 引継ぎ=Step9 / 講評=Step10）。チェックの二重実装はしない。
- 最終ステップの提出ボタンは既存の persist('submitted') をそのまま呼ぶ。

## 5. 流用の考え方

- ステップは `{ id, question, isComplete(state), skip?(state), render }` の宣言的な配列で定義する。
- ただし**汎用フローエンジンは今は作らない**。抽象化は2例目（面談記録など）が出たときに、
  実例2つから共通部分を抜く。1例で抽象化すると外す（このプロジェクトの過去の教訓と同じ方針）。

## 6. ⑭（AI活用）との接続 — 本設計ではフック位置だけ確保

- Step 10（講評）: 「AIに下書きを作らせる」ボタンの置き場。材料は同じ画面の入力
  （単元・達成度・テスト結果・様子マーク・引継ぎ）が全部揃っているので、ここが最適位置。
- Step 11（提出前）: AI講評チェック（不足・敬語・具体性）の置き場。
- 本設計では**ボタンもAPIも実装しない**。⑭の設計で別途決める（チャット返信AIと合わせて）。

## 7. 実装フェーズ

1. **Phase 1**: モード切替＋ステップ枠組み＋既存セクションをステップに載せ替え（見せ方の変更のみ）。
2. **Phase 2**: ステップ専用の磨き込み（1問1画面の文言・大きなタップ領域・「あとで書く」）。
3. **Phase 3**: ⑭のAI（講評下書き・講評チェック）。別設計。

## 8. 確認済み（2026-08-31）

1. 方式=ゆるいガイドバー（§3）。ウィザード型は不採用。既定=バー表示・×で消せる・選択記憶。
2. ステップ構成（§4 の11問・時系列）はこの案で確定。
3. 実装フェーズ: Phase 1 でガイドバー＋完了判定＋スクロール誘導まで。AIは⑭の設計で。

## 9. 2026-09-03 改訂 — 14問に組み替え

モックで実際に書いてみた結果、§4 の11問を **14問**に組み替えた。
モック: [報告書の書かせ方](https://claude.ai/code/artifact/1f4cf178-de97-4771-b3c9-e74815ebc2cf)

### 9-1. なぜ変わったか

**★「授業前に分かること」と「授業が終わらないと分からないこと」が混ざっていた。**
とくに指導範囲は「どこから」なら授業開始時に聞けるが、「どこまで」は講評を書いた後にしか
確定しない。1つの質問にしていたので、授業の途中では答えられなかった。

| 1  | 今日の様子で当てはまるものは？ | 遅刻・宿題未実施のトグルピル |

### 9-3. 変更点

| # | 変更 | 理由 |
| --- | --- | --- |
| 1 | **指導範囲を開始/終了に分ける** | 「どこまで」は講評の後にしか分からない |
| 2 | 今日の演習の正答率も講評の後へ | 同上 |
| 3 | 学校進度を3番目に | 授業前に分かっていることを先に片づける |
| 4 | 次回の予定を引継ぎの隣に | 次回の話は続けて聞く |
| 5 | 次回の予定に「表から選ぶ」を追加 | 進行表からの自動に加えて手でも選べるように |
| 6 | **宿題をテキスト名とページに分ける**＋テキスト名の自動補完 | タイピングを減らす（講師UIの方針） |
| 7 | 進捗の丸をクリックでその質問に戻れる | 戻る導線が無かった |
| 8 | 最後の「書いてないところ」から該当質問へ飛べる | 指摘だけでナビが無かった |
| 9 | フローティングカードから提出できる | 最後まで書いたらそのまま出せる |

### 9-4. 変えない大原則

- ★**表示側のフィールドは1つのまま。** 開始と終了で分けて聞くが、書き込む欄は同じ。
  質問の分割は聞き方の問題であって、データの形は変えない。
- ★**保存経路を増やさない**（§2）。ガイドはプレゼンテーション層だけ。
- 完了判定は既存の `validateForSubmit` をステップ単位に割り当てる（§4）。
  指導範囲は開始・終了のどちらのステップでも同じ判定を見る。

### 9-5. 実装との差分

ガイドバーは **PR #102 で実装済み**（`src/lib/lesson-reports/guideSteps.ts`・現在10問）。
現行の並びは mood / taught / homework-check / check-test / school-progress / goal /
next-plan / homework-assign / handover / review。
§9-2 に合わせて **`guideSteps.ts` の定義配列を組み替える**のが作業の中心で、
フォーム本体（`/lesson-reports/[scheduleEntryId]`）の入力欄は原則そのまま使う。

例外は2つ。**宿題の入力欄をテキスト名とページに分ける**（自動補完のための datalist を足す）ことと、
**次回の予定に「表から選ぶ」を足す**こと。この2つだけはフォーム側の変更になる。

### 9-6. AIとの同居

この画面には ⑬のガイドに加えて **講評を整える** と **授業中ポップアップ**（連絡事項の監視）が乗る。
3つが同じ画面を取り合うので、置き方は [ai-features-integration-plan.md](./ai-features-integration-plan.md) §2-1 に集約した。
★**ポップアップはガイドの質問に答えている最中は出さない。**
